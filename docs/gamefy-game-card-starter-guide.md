# DZMM Gamefy 游戏卡制作入门指南

适合第一次制作游戏卡的创作者：从创建游戏、编写 H5，到调试、发布和上架；也介绍多人对战与群聊 bot 如何连接。

最重要的一点：游戏卡是入口，H5 是游戏界面与代码。简单单机游戏可以先用平台能力完成，不一定需要自己的服务器；多人实时游戏还需要处理共享状态、身份和并发，不能只做一张可点击的网页。

整理日期：2026 年 10 月 13 日。平台操作与命令依据所提供的《DZMM Gamefy 开发者文档》；会员要求、界面和 CLI 参数以你所用站点的最新文档为准。

## 一 开始前准备什么

- 一个你自己的平台账号，以及符合平台当前开发要求的会员资格。所提供文档要求 VIP1 及以上。
- 一个明确的小玩法：玩家进入后做什么、如何获胜、是否需要保存进度。
- 游戏名称、封面、简介和作者说明；使用有权使用的图片与音频。
- 如果选择本地开发，准备 Node.js/npm、代码编辑器和 Connected Dev CLI；使用网页工坊则不必先安装 CLI。

开发密钥必须由你自己创建。不要借用别人的密钥，不要把密钥发到群里、写进游戏脚本或提交到 Git。

## 二 选择开发方式

| 方式 | 适合情况 | 注意事项 |
| --- | --- | --- |
| 网页 Workbench 工坊 | 初次尝试，直接在网页编辑和预览 | 修改后先保存，再发布 |
| Connected Dev CLI | 本地编辑、Git 管理、自动化测试或让编程助手协助 | 本地文件与工坊编辑区不会自动同步 |

两种方式都可以发布游戏。不要两边同时改同一张卡，否则容易覆盖更新。

第一次建议做一个按钮交互或小型单机游戏，先完整走通发布流程，再做象棋、斗地主等多人游戏。

## 三 网页制作的基本流程

1. 在你使用的平台进入创作者中心，创建自己的游戏卡并打开 Workbench。
2. 编辑 `publish/index.html`、样式和脚本，用预览检查效果。
3. 设置合适的横屏或竖屏方向；手机上检查按钮、文字和输入框。
4. 保存代码，然后发布游戏版本。
5. 补齐名称、封面和作者说明，在角色详情页提交上架审核。
6. 审核通过后，用另一个普通玩家账号打开测试。

**发布代码不等于公开上架。** 按平台文档，未上架时创作者能预览，但普通玩家访问入口可能收到 403，访问详情页可能收到 404。不要只因为自己能打开就认为好友也能玩。

## 四 本地开发的基本流程

以下以 `https://www.aikda.com` 为示例。若你在其他站点创建账号和密钥，应使用那个站点，不要混用域名或把密钥交给不明站点。

开发者密钥页面：<https://www.aikda.com/studio/game-creation/dev-keys>。优先查看该页“上手指南”，使用平台给出的安装命令。

### 安装和授权

```bash
curl -fL -o dzmm-gamefy-cli.tgz https://www.aikda.com/api/app/cli/download/latest
npm install -g ./dzmm-gamefy-cli.tgz
gamefy auth login --base-url https://www.aikda.com
```

按终端提示，在浏览器打开授权页面并输入验证码。这里授权的是开发者账号，不是未来玩家的账号。不要把真实密钥粘贴到游戏源码中。

### 创建本地项目并选择游戏

```bash
mkdir my-game
cd my-game
gamefy init
gamefy docs
gamefy dev
```

`gamefy init` 按提示选择自己的游戏；文档还提供 `--new` 新建入口和 `--game` 链接选卡方式，具体用法先看安装版本的帮助。`gamefy docs` 下载该站点当前文档，应该一并提供给编程助手。

本地测试不是完全离线模拟：SDK 功能可请求真实平台服务，AI 调用可能消耗开发者自己的积分。无需 AI 的游戏不要为了制作游戏而添加 AI 调用。

### 检查和发布

```bash
gamefy status
gamefy check --reload --slow
gamefy deploy --dry-run
gamefy deploy --verify
```

前三步先看状态、检查运行并预检查发布；最后一步才实际更新线上代码。`check` 不能代替完整游玩测试。执行前用 `gamefy --help` 核对当前版本支持的命令。

如果遇到 `revision_conflict`，先保留本地改动，对比线上版本再合并，不要直接 `--force` 覆盖。CLI 发布之后若回网页继续改，应先通过工坊“从线上恢复”同步最新代码，并保住未发布改动。

## 五 文件怎样放

```text
my-game/
├── publish/
│   ├── index.html
│   ├── style.css
│   ├── game.js
│   └── assets/
│       └── cover.png
└── functions/
    └── score.ts
```

`publish/index.html` 是必需入口。玩家使用的脚本、样式和图片放在 `publish/` 内，引用使用 `./assets/cover.png` 等相对路径。文件名和路径使用 ASCII 字符，不用中文文件名；页面文字可以是中文。

`functions/` 是可选的平台服务端函数，不需要就不建。它不是一台任意使用的服务器，不能照搬 Node.js/Python 服务、Express/Flask 或监听端口的程序；可用能力要查平台文档。

发布目录里的文件不能当作秘密存储：即使卡未上架，知道静态资源地址的人也可能访问。不要放密码、数据库连接串、开发密钥或私人数据；隐藏提示词也不等于安全保存秘密。

## 六 SDK 和运行环境

游戏运行在平台的 iframe 沙箱内，平台注入 `window.dzmm`。通过它调用玩家信息、存档及其他平台能力，而不是读取主站 Cookie 或父页面。

```javascript
// 在平台 SDK 已就绪后调用，并在实际代码中处理失败情况。
const player = await window.dzmm.user.info();
const uid = player.id;
```

注意以下边界：

- 不依赖 `localStorage`、`sessionStorage`、Cookie 或 IndexedDB，平台文档说明它们受沙箱限制；存档使用 `dzmm.kv`，具体接口按当前文档实现。
- SDK 调用是异步的，按钮需要防重复点击，并显示加载与失败状态。
- 玩家 UID 与登录 token 不同。平台页面已登录，不代表游戏一定拿到有效 token；所提供文档说明 token 为空可能是未登录或签发失败，不要把所有空值都显示成“玩家未登录”。
- 不循环高频请求 token；先看实际错误与平台限制，合并重复请求。
- 所提供文档示例允许表单提交，但我们实际测试过的运行入口缺少 `allow-forms`。为兼容不同入口，按钮显式绑定点击事件，不依赖原生表单提交。
- 手机布局考虑 `100dvh`、安全区、键盘弹起和窗口 resize；实际检查内容是否溢出、输入框是否遮挡操作。

## 七 多人游戏比单机多什么

一个可玩的多人游戏，至少要有权威牌局或棋局状态、房间与席位、并发控制、服务端计时、断线恢复、胜负结算和消息同步。

客户端提交“我想做这个操作”，服务端判断是否合法。不能让浏览器直接改数据库、决定胜负、发奖励，或把所有人的隐藏手牌发给每个客户端后只用 CSS 藏起来。

简单共享玩法可以研究平台服务端函数和 KV；涉及实时对战时，先确认它们是否满足原子更新和同步需求。若选择自己的后端，应通过 HTTPS API 接入，数据库仅由后端访问，并验证实际沙箱网络请求与跨域配置。

### 身份校验的区别

平台 SDK 能提供 UID，但客户端提交给自建服务器的 UID 可以被修改。只信任 UID 能简化接入，却不能防止别人冒充玩家。在有隐藏手牌、奖励、货币或管理权限的游戏中尤其要重视这个问题。

较可靠的做法是按平台契约验证签名凭证，包括签名、签发者、游戏 audience、有效期和用户标识。若平台凭证暂不可用，应先查明原因或设计另外的可信验证流程，不要把 UID 模式宣传为安全认证。

### 重连和倒计时

刷新页面只重新获取状态，不能重新发牌、重置计时或丢失席位。截止时间由服务端保存；同一请求重试不得重复出牌、入座或结算。正在进行的游戏与等待中的房间要分别处理退出。

## 八 群聊 bot 怎样发送游戏入口

群聊指令不是游戏卡自带功能，需要另外接入有权限的 bot。可设计为：群友发送指令，后端创建房间，bot 发送游戏分享卡，再单独发房间号或入座码等文字。

在已观察到的平台消息中，分享游戏卡的 content 结构为：

```json
{
  "type": "share",
  "shareType": "character",
  "resourceId": "你自己的游戏卡ID"
}
```

这只是消息内容示例，不是完整发送接口，也不包含认证信息。接入时按你自己的 bot 协议封装。

分享卡和文字说明是两种消息，不应拼成一条长链接文本。游戏卡 ID、房间 ID、入座码和开发密钥是不同的东西：卡 ID 指向游戏，房间 ID 指向一局，入座码控制加入，开发密钥仅用于开发授权。

## 九 发布前检查

- 手机能完成一次完整游戏，不只是看到首页。
- 开发者和普通玩家账号都测试过；多人游戏使用多个不同账号。
- 刷新、关闭重开、断网重连、重复点击均有明确结果。
- 未登录或 SDK 出错时有可恢复提示，不无限重试。
- 图片和脚本全部加载，没有中文路径或本地绝对路径。
- 没有把秘密、其他玩家手牌或数据库内容输出到浏览器及日志。
- 发布成功后另行完成上架审核；作者说明准确介绍玩法，遵守当前审核规则，不放无关引流信息。
- 更新前保留旧代码；多人后端更新前另备份数据库。
