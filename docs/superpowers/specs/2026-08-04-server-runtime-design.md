# DZMM 服务器运行底座设计

## 目标

重写机器人为可长期运行的服务器应用：核心玩法和数据不依赖浏览器；浏览器仅是没有官方 API 时的消息适配器。管理 Web 通过服务器 IP 加端口访问；用户只在登录或人工滑块验证时操作临时虚拟桌面。

本规格只覆盖运行底座、消息可靠性、登录态和管理控制。新玩法、经济规则和指令库在底座验收后单独设计。

## 已确认条件

- 群聊平台没有官方机器人 API、Webhook 或 WebSocket。
- 登录方式为邮箱密码，偶尔出现必须人工拖动的滑块验证。
- 服务器为 Ubuntu 24.04、2 核 / 4GB、磁盘余量约 15GB，且正在运行其他服务。
- 管理端暂时使用 HTTP 的 `服务器 IP:端口`；用户明确接受该访问方式。
- 本地电脑不作为常驻节点。
- 现有服务器的 OpenClaw Chrome（CDP 9222）及其他服务不得复用、停止或修改。

## 服务边界

### 1. 核心服务：`dzmm-core`

核心服务是唯一的业务与数据写入者。它提供内部 API 和管理 API，并负责：

- 消息去重、顺序处理和幂等回复。
- 指令路由、用户身份、经济流水、玩法状态和定时任务。
- 将待发送内容写为持久化出站任务。
- 浏览器登录状态、Worker 心跳、失败原因和审计事件。
- 管理 Web 所需的状态、日志摘要和配置接口。

核心服务只监听 `127.0.0.1`；不直接控制 Chrome。

### 2. 浏览器 Worker：`dzmm-browser-worker`

Worker 使用单独的 Chrome profile 和独立 CDP 端口，仅负责：

- 读取群聊消息并提交给核心服务。
- 从核心领取待发送任务、调用网页发送并确认结果。
- 上报自身健康状态、页面状态及登录失效状态。
- 在核心要求登录时停止普通监听，释放独占的浏览器 profile。

Worker 不能直接读写 PostgreSQL，不能自行结算指令，也不能绕过核心发送任意回复。

### 3. 管理 Web：`dzmm-admin-web`

管理 Web 是单独的前端服务，对外监听一个未与现有服务冲突的高位端口。它只调用核心管理 API，提供：

- Worker、核心、登录态和队列状态。
- 启动、停止、重启监听。
- 指令/配置和审计日志浏览。
- “开始登录验证”与“结束登录验证”控制。
- 临时 noVNC 控制台入口。

管理端使用一个独立管理员凭据。由于当前为 HTTP，初期只暴露必要功能，不存储服务器 SSH 凭据或群聊密码。

## 数据与可靠性

新建独立 PostgreSQL 数据库和角色，不使用服务器中现有应用数据库。初始表包括：

- `inbound_messages`：平台消息 ID 唯一约束、收到时间、原始内容、处理状态。
- `outbound_messages`：回复内容、关联入站消息、状态、发送 lease、lease 令牌、重试次数与最终平台发送 ID。
- `worker_instances`：心跳、版本、浏览器状态和最近错误。
- `worker_commands`：由核心持久化的浏览器控制命令、领取 lease、lease 令牌、执行结果和审计关联。
- `login_sessions`：状态机记录，不保存明文密码。
- `audit_events`：管理操作、登录切换、Worker 异常和人工恢复记录。

处理流程：

1. Worker 读取平台消息，并以平台稳定消息 ID 提交核心。
2. 核心在一个数据库事务中插入入站消息；唯一冲突表示已经处理，直接返回。
3. 核心执行指令，在同一事务中写入经济/玩法变化与一条待发送出站消息。
4. Worker 以带 lease 和随机 lease 令牌的原子领取方式领取出站消息；发送成功回执必须匹配 Worker 身份、令牌且 lease 未过期。崩溃后的过期 lease 可以安全重试。
5. 管理 Web 的监听、重启浏览器和登录请求都先写为 `worker_commands`；Worker 领取并回执，不能由管理端直接控制 Chrome。
6. 查询类命令和发送失败不会重复产生经济流水。

## 登录与人工验证

Chrome profile 只属于 `dzmm-browser-worker`，目录位于独立受限路径，例如 `/var/lib/dzmm-browser/profile`，服务用户独占访问。

- 日常：Worker 使用 `--headless=new` 运行。
- 需要邮箱密码或滑块：核心将登录状态转为 `auth_required`，停止 Worker。
- 管理员从 Web 发起登录，临时服务启动 `Xvfb + Fluxbox + Chrome + x11vnc/noVNC`，使用同一 profile。
- 管理员在浏览器 Web 页面中亲自输入密码、完成滑块；系统不尝试自动破解或规避人机验证。
- 登录成功由浏览器状态检测确认；临时服务关闭，Worker 以无头模式重新启动。
- noVNC 仅在登录状态存在时启动；正常运行期间不占用虚拟桌面资源。

临时虚拟桌面和无头 Worker 绝不同时使用同一个 profile。

## 部署与资源

不使用 Docker，避免在现有服务器上额外引入镜像和守护进程。部署使用专用 Linux 用户、Python 虚拟环境、独立系统目录与三项 systemd 服务：

- `dzmm-core.service`
- `dzmm-browser-worker.service`
- `dzmm-admin-web.service`

登录时额外由核心控制临时认证服务。每项常驻服务都设置开机自启、崩溃后延迟重启、受限文件权限和独立 journald 标识。

建议初始端口：

- 核心 API：`127.0.0.1:18120`
- Worker CDP：`127.0.0.1:19222`
- 管理 Web：`0.0.0.0:18090`
- noVNC：仅认证时监听 `127.0.0.1:16080`，由管理 Web 临时代理。

最终端口在部署前再次检查，避免冲突。

## 验收标准

1. 重启 Worker 不丢失、重复处理或重复回复已确认消息。
2. 在 Worker 离线期间核心数据和管理 Web 可用。
3. 发送失败并重启 Worker 后，一条待发送回复最多完成一次平台可见发送。
4. 登录态失效后，系统进入 `auth_required` 而不是循环发送或停止核心。
5. 管理员可从管理 Web 打开临时 noVNC，自行完成真实滑块验证；结束后无头监听恢复。
6. 服务器重启后，三个常驻服务自动恢复，且不得影响现有 Chrome 9222、OpenClaw、MySQL、PostgreSQL、Redis、Nginx 或其他现有服务。
7. 资源稳定：正常无头运行不常驻虚拟桌面；磁盘监控在低于 5GB 余量时发出管理告警。

## 非目标

- 本阶段不导入旧项目数据、不复刻旧玩法、不实现 AI、商店或经济指令。
- 不尝试绕过邮箱验证、人机滑块或平台风控。
- 不复用或修改服务器现有的 Chrome profile、数据库、Redis、端口 9222 或应用服务。
