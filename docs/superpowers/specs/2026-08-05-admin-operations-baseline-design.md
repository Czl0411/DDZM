# 管理端运营基础体验设计

## 目标

让运营者能够稳定修改配置和管理增长型数据：写操作有明确进行状态、防重复提交和可读错误；员工、商品列表按服务端分页读取。

## 范围

- 统一所有写操作的进行状态：指令启停、回复模板、经济规则、活跃度规则、上架物品和浏览器运维操作。
- 进行中按钮禁用并显示对应动作的进行文案；同一动作不重复发起请求；完成后恢复可操作状态。
- 请求失败时显示接口返回的具体原因；成功后仅刷新受影响的区域。
- 员工和物品列表使用服务端分页，默认每页 20 条；页面显示当前范围、总数和上一页/下一页按钮。
- 写入商品后保留当前商品页；列表刷新不跳转到其他管理视图。

## 不在范围内

- 指令库不分页。它是固定的配置集合，不随成员量增长。
- 不增加搜索、筛选、编辑或删除商品功能。
- 不改变游戏数据、权限模型或现有指令语义。

## 接口与数据流

核心服务为员工和物品接口接收 `page`、`page_size` 查询参数，并返回：

```json
{
  "items": [],
  "page": 1,
  "page_size": 20,
  "total": 0,
  "pages": 0
}
```

管理端原样代理该响应。员工按入职时间倒序，商品按创建时间倒序；两者使新数据出现在第一页。

前端以当前视图各自维护页码。分页按钮只改变当前列表的页码并重新读取该列表。统一请求封装在遇到非成功响应时读取 JSON `detail` 或纯文本错误，作为面向运营者的反馈。

## 交互状态

每个写操作在发起时保存原按钮文本，设置进行中文案并禁用按钮；同一控件再次触发直接忽略。请求结束后恢复按钮状态。成功时显示成功提示并刷新相关数据；失败时显示具体原因且保留用户已输入的内容。

## 验证

- 核心与管理端测试覆盖分页边界、总数和页码验证。
- 前端回归覆盖所有写操作使用统一进行状态与错误读取行为。
- 全量测试、编译检查和线上健康检查通过后部署。
