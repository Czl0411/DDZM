# 每日活跃度玩法设计

## 目标

为已入职成员提供按当天有效发言累积的活跃等级、北京时间 00:00 自动发放的摸鱼币奖励，以及定时推送的今日收益榜。玩家只看到等级与今日收益，不公开原始字数；运营者可在管理端调整各等级门槛和奖励。

## 已确认规则

- 统计时区统一为 `Asia/Shanghai`，每天在北京时间 00:00 切换与结算。
- 仅已入职成员的非指令纯文本计入；去掉全部空白字符后按字符数累计。
- 图片、表情、空消息、以 `/` 开头的指令和机器人消息不计入。
- 每日结束后自动入账，不能要求玩家手动领取。
- 玩家指令：
  - `/我`：展示昵称、当前摸鱼币余额、今日 `LV` 与今日收益；`/me` 为同义别名；不显示字数和零点说明；
  - 不提供收益榜查询指令；收益榜由机器人主动推送。
- 默认配置如下，运营者均可修改：

| 等级 | 累计有效字数门槛 | 每日奖励（摸鱼币） |
| --- | ---: | ---: |
| LV1 | 10 | 1 |
| LV2 | 25 | 2 |
| LV3 | 60 | 3 |
| LV4 | 90 | 4 |
| LV5 | 140 | 5 |
| LV6 | 190 | 6 |
| LV7 | 250 | 7 |
| LV8 | 330 | 8 |
| LV9 | 410 | 9 |
| LV10 | 500 | 10 |

未达到 LV1 的成员显示 `LV0` 和 0 奖励。今日收益只累计当天所有正向入账；包括入职奖励、打卡奖励、在北京时间 00:00 入账的活跃度奖励、游戏奖励以及后续新增的所有正向来源。消费、游戏扣币、惩罚扣币和其他负向变动只影响余额，不减少今日收益，也不影响今日收益榜。余额允许为负数。

## 数据模型与结算

新增每日活跃记录，唯一键为 `user_id + activity_date`，只保存当天有效字数。新增每日结算记录，唯一键为 `user_id + activity_date`，保存结算时等级、奖励和结算时间。新增收支流水，保存用户、变动金额、来源类型和北京时间发生时间；正数代表收入，负数代表扣除。新增收益榜推送时段配置，默认 `12:00`、`16:00`、`20:00`、`23:59`；新增收益榜推送记录，唯一键为 `report_date + report_time`，用于确保每个已配置时段至多推送一次。

Core 在成功去重并保存每条入站消息后，对符合规则且已入职的成员累加当天记录。等级由当前管理端配置即时计算，因此门槛或奖励改动会影响尚未结算的当天展示和后续结算。每次余额发生变动时，Core 在同一事务同步写入收支流水；当前覆盖入职奖励、每日打卡和活跃度结算，后续游戏奖励或惩罚也必须通过这条流水写入。

浏览器 Worker 每轮向 Core 请求一次结算检查。Core 以北京时间当前日期找出所有尚未结算的历史日期，按结算时配置计算奖励、更新用户余额并写入结算记录。余额更新和结算记录写入位于同一事务；唯一键保证 Worker 重启、补偿检查或重复调用都不会重复发币。Worker 停机跨过 00:00 时，会在恢复后的下一轮自动补结算。

当天活动数据在零点后仍保留用于审计和结算查询，但玩家指令始终只查询当天的记录。今日收益和收益榜按收支流水中当天金额大于 0 的记录求和；当日没有正向收益的成员不进入收益榜。

浏览器 Worker 每轮也会请求 Core 检查收益榜推送。Core 在每个已配置的北京时间时段后为当前日期生成前 10 名收益榜；只要当天至少存在一笔正向收入，就创建一条可重试的系统出站消息。当天没有正向收入则跳过该时段。推送记录与出站消息在同一事务中创建，保证重启、重复检查或延迟补偿不会同一时段重复发到群内。

## 管理端

在既有“玩法配置”页面增加“日活跃度”摘要卡片，主页面只显示当前规则概览与“编辑日活跃度”按钮。点击按钮打开弹窗，弹窗展示 10 行等级、累计字数门槛和每日奖励；运营者可一次性修改全部行并保存。

收益榜推送时段与日活跃度配置位于同一弹窗，运营者可用时间控件添加或删除时段；默认四个时段可编辑。时段必须是北京时间的 `HH:MM`、互不重复且至少保留一个。保存校验要求：等级固定为 1–10；门槛与奖励均为非负整数；门槛严格递增；奖励上限沿用小额经济的 0–999。保存成功后关闭弹窗、刷新摘要并显示中文成功提示。管理端可以显示门槛，因为它是运营配置；玩家侧一律不显示原始字数。

`/我` 进入指令库，支持启停和与现有指令一致的回复模板编辑。`/me` 只作为 `/我` 的输入别名，不单列配置。模板可使用现有 `{昵称}`、`{余额}`、`{货币}`、`{日期}`，并新增仅在对应场景可用的 `{活跃等级}`、`{今日收益}`。收益榜推送使用固定的系统格式，展示标题、推送时间、排名、昵称与今日收益；它不在指令库中出现。

## 接口与组件边界

- Repository：只处理活跃记录累加、等级计算、收支流水、今日收益榜查询、定时推送去重、配置读写和幂等结算。
- CoreService：在已去重入站消息后触发活动累计；命令处理继续只负责生成回复。
- Core API：提供日活跃度与收益榜推送时段的读取/更新，以及 Worker 使用的受令牌保护结算与收益榜推送检查接口。
- Browser Worker：仅调用结算与收益榜推送检查，不持有活动状态、奖励规则或计划时段状态。
- Admin：通过现有 CoreClient 读取/保存配置，并提供弹窗交互。

## 验证

- 仓库测试：计数规则、未入职成员排除、字数跨等级、正向流水累计、负向流水排除、收益榜排序与前 10、四个计划时段、空榜跳过、推送去重、默认/非法配置、零点结算、重复结算和停机补偿均覆盖。
- 指令测试：`/我`、`/me` 不泄露字数，且模板变量、指令启停和 `/帮助` 正确生效。
- API/Admin 测试：管理端读取、修改与校验 10 条规则和推送时段；结算接口受令牌保护。
- Worker 测试：每轮调用结算检查且不影响现有监听、发送、登录流程。
- 完整测试套件通过后再部署；部署后用两个已入职测试账号验证累计、排名和一次零点结算。
