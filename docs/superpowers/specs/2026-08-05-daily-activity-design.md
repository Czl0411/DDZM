# 每日活跃度玩法设计

## 目标

为已入职成员提供按当天有效发言累积的活跃等级、每日活跃榜和北京时间 00:00 自动发放的摸鱼币奖励。玩家只看到等级与奖励，不公开原始字数；运营者可在管理端调整各等级门槛和奖励。

## 已确认规则

- 统计时区统一为 `Asia/Shanghai`，每天在北京时间 00:00 切换与结算。
- 仅已入职成员的非指令纯文本计入；去掉全部空白字符后按字符数累计。
- 图片、表情、空消息、以 `/` 开头的指令和机器人消息不计入。
- 每日结束后自动入账，不能要求玩家手动领取。
- 玩家指令：
  - `/我`：展示昵称、当前余额、今日 `LV`、预计自动入账的奖励与北京时间 00:00 的发放说明，不显示字数；`/me` 为同义别名；
  - `/活跃榜`：展示当天前 10 名的昵称、`LV` 和预计奖励，不显示字数。
- 默认配置如下，运营者均可修改：

| 等级 | 累计有效字数门槛 | 每日奖励（摸鱼币） |
| --- | ---: | ---: |
| LV1 | 10 | 1 |
| LV2 | 25 | 2 |
| LV3 | 60 | 3 |
| LV4 | 90 | 4 |
| LV5 | 140 | 5 |
| LV6 | 190 | 6 |
| LV7 | 250 | 7 |
| LV8 | 330 | 8 |
| LV9 | 410 | 9 |
| LV10 | 500 | 10 |

未达到 LV1 的成员显示 `LV0` 和 0 奖励；不向排行榜输出。

## 数据模型与结算

新增每日活跃记录，唯一键为 `user_id + activity_date`，只保存当天有效字数。新增每日结算记录，唯一键为 `user_id + activity_date`，保存结算时等级、奖励和结算时间。

Core 在成功去重并保存每条入站消息后，对符合规则且已入职的成员累加当天记录。等级由当前管理端配置即时计算，因此门槛或奖励改动会影响尚未结算的当天展示和后续结算。

浏览器 Worker 每轮向 Core 请求一次结算检查。Core 以北京时间当前日期找出所有尚未结算的历史日期，按结算时配置计算奖励、更新用户余额并写入结算记录。余额更新和结算记录写入位于同一事务；唯一键保证 Worker 重启、补偿检查或重复调用都不会重复发币。Worker 停机跨过 00:00 时，会在恢复后的下一轮自动补结算。

当天活动数据在零点后仍保留用于审计和结算查询，但玩家指令始终只查询当天的记录。

## 管理端

在既有“玩法配置”页面增加“日活跃度”摘要卡片，主页面只显示当前规则概览与“编辑日活跃度”按钮。点击按钮打开弹窗，弹窗展示 10 行等级、累计字数门槛和每日奖励；运营者可一次性修改全部行并保存。

保存校验要求：等级固定为 1–10；门槛与奖励均为非负整数；门槛严格递增；奖励上限沿用小额经济的 0–999。保存成功后关闭弹窗、刷新摘要并显示中文成功提示。管理端可以显示门槛，因为它是运营配置；玩家侧一律不显示原始字数。

`/我` 和 `/活跃榜` 进入指令库，支持启停和与现有指令一致的回复模板编辑。`/me` 只作为 `/我` 的输入别名，不单列配置。模板可使用现有 `{昵称}`、`{余额}`、`{货币}`、`{日期}`，并新增仅在对应场景可用的 `{活跃等级}`、`{活跃奖励}`、`{活跃榜}`。

## 接口与组件边界

- Repository：只处理活跃记录累加、等级计算、排行榜查询、配置读写和幂等结算。
- CoreService：在已去重入站消息后触发活动累计；命令处理继续只负责生成回复。
- Core API：提供日活跃度配置的读取/更新，以及 Worker 使用的受令牌保护结算检查接口。
- Browser Worker：仅调用结算检查，不持有活动状态或奖励规则。
- Admin：通过现有 CoreClient 读取/保存配置，并提供弹窗交互。

## 验证

- 仓库测试：计数规则、未入职成员排除、字数跨等级、排行榜排序与前 10、默认/非法配置、零点结算、重复结算和停机补偿均覆盖。
- 指令测试：`/我`、`/me` 和 `/活跃榜` 不泄露字数，且模板变量、指令启停和 `/帮助` 正确生效。
- API/Admin 测试：管理端读取、修改与校验 10 条规则；结算接口受令牌保护。
- Worker 测试：每轮调用结算检查且不影响现有监听、发送、登录流程。
- 完整测试套件通过后再部署；部署后用两个已入职测试账号验证累计、排名和一次零点结算。
