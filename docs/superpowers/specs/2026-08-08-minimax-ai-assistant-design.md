# Minimax AI 总监事设计

## 目标

将群机器人扩展为可艾特对话的“总监事”。现有指令、经济、随机事件和游戏规则仍由规则引擎处理，AI 只回答普通群聊中的艾特内容。

## 触发与边界

- 仅当群成员发送 `@总监事 内容` 时创建 AI 请求；空内容不触发。
- 所有 `/指令` 优先按既有规则处理，不调用模型。
- 随机事件、躲猫猫、记忆考核和谁是卧底的流程消息仍由既有规则处理，不交给 AI。
- 第一版不处理私聊。
- 未入职成员不调用模型，回复其先使用 `/入职 名字`。

## 配置

管理员在“AI 总监事”页面配置：

- AI 开关；
- 机器人人设；
- 系统提示词；
- 各职位等级的每日调用上限；
- 超额时的固定回复；
- 模型失败时的固定回复；
- 单次回复最大字符数和模型请求超时。

Minimax 的 API Key 仅从运行环境读取，不在管理端、数据库、日志或接口响应中出现。模型标识与 API 地址也由环境变量提供，避免将服务商连接密钥写入业务数据。

默认人设为“摸鱼公司群的美女总监事”：表达简短、有公司群调侃感，但不代替系统执行命令、经济结算或游戏裁判行为。

## 数据模型

新增以下持久化记录：

- `ai_assistant_settings`：单例配置，包括人设、系统提示词、开关、超额/失败文案、回复上限和超时；
- `ai_rank_quotas`：职位等级与对应的每日可调用次数；
- `daily_ai_usage`：用户 ID、北京时间日期与已使用次数；
- `ai_requests`：入站消息 ID、发起人、状态、重试次数、模型输出或失败摘要、创建和完成时间。

`ai_requests` 只引用现有入站消息，不重复保存原始群消息内容。数据库仍由核心服务唯一写入。

## 处理流程

1. 核心收到群消息，先执行既有指令和玩法路由。
2. 普通艾特消息通过身份和日额度校验后，在同一事务中递增 `daily_ai_usage` 并创建唯一 AI 请求。
3. 独立 AI Worker 使用 lease 领取待处理请求，调用 Minimax。
4. Worker 将成功文本或失败结果回写核心 API；核心写入现有出站队列。
5. 浏览器 Worker 继续只负责发送队列中的消息。

额度按北京时间每日 00:00 重置，按用户 ID 计数。并发艾特时，只有未超过职级额度的请求可成功创建。模型调用失败或超时不返还额度，防止故障期间无限重试消耗系统。

最终发送给 Minimax 的系统提示词由固定运行规则、管理员系统提示词和管理员人设顺序组成。固定运行规则要求模型不得伪造系统状态、执行指令、修改经济/游戏结果，且只基于当前艾特内容回答。

## 可靠性与安全

- AI 请求使用持久化队列和 lease，避免慢模型阻塞消息监听；
- 对同一入站消息保持幂等，只创建一条 AI 请求；
- 到达超额次数时直接发送配置文案，不调用模型；
- 调用失败、超时或无有效输出时发送配置的失败文案；
- 输出进入既有出站队列并沿用消息拆分限制；
- 不将 API Key、完整请求头或模型密钥写入审计与错误日志。

## 验证

- 单元测试：艾特检测、指令优先、未入职拦截、按北京日期额度、并发额度、请求幂等、提示词顺序、失败回退；
- 核心 API 测试：配置读写、AI 请求领取与回写、敏感字段不出现在响应中；
- 管理端测试：配置页面、按职位额度保存与错误反馈；
- 部署验证：三个既有服务与新增 AI Worker 可启动，模拟模型响应可入队并发送。
