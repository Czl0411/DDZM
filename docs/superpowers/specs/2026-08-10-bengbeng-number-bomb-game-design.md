# 蹦蹦数字炸弹游戏设计

## 目标

新增一个不涉及金币的多人连续轮次游戏“蹦蹦数字炸弹”。玩家在群内报名，在每轮中分别私聊机器人提交 `1–100` 的整数；全部提交后，机器人按平均数乘以 `0.8` 计算目标值，在群内公开计算过程、偏离排名、胜出者和受罚者。

游戏每三轮循环两轮真心话和一轮大冒险。胜出者负责出题并监督受罚者，机器人只负责主持、计算和公布结果，不生成具体惩罚内容。

## 指令与参与资格

只有已经通过 `/入职 名字` 建立员工资料的玩家可以创建或参加游戏。

| 阶段 | 指令 | 行为 |
| --- | --- | --- |
| 无游戏 | `/蹦蹦数字炸弹 6` | 创建目标人数为 6 的报名，发起者自动加入 |
| 报名中 | `/加入` | 立即加入当前报名，达到目标人数后自动开始第 1 轮 |
| 报名中 | `/退出` | 立即取消报名；最后一人退出后结束报名 |
| 报数中或等待继续 | `/加入` | 非当前参与者申请加入下一轮 |
| 报数中或等待继续 | `/退出` | 当前参与者申请下一轮退出；候选者取消下一轮加入 |
| 报数中 | 私聊 `/报数 29` | 提交并锁定本人本轮的整数 |
| 有效轮结算后 | `/继续` | 任一当前参与者应用人员变更并开始下一轮 |
| 游戏存在 | `/结束游戏` | 任一当前参与者立即结束整场 |

创建目标人数必须是 `3–10` 的整数。游戏开始后的下一轮也必须保持 `3–10` 人。

没有每日发起次数限制，不冻结、扣除或奖励金币。

## 游戏生命周期

游戏具有以下状态：

1. `signup`：报名中。发起者自动成为第一名玩家，达到创建命令指定的人数后立即开始第 1 轮。
2. `collecting`：本轮报数中。参与名单锁定，等待所有当前参与者私聊提交数字。
3. `waiting_continue`：有效轮已经结算，等待当前参与者发送 `/继续`。
4. `ended`：主动结束、超时、下一轮人数不足或报名无人后终止。

第 1、2 轮为真心话，第 3 轮为大冒险，此后每三轮重复。等价判定为：轮次能被 3 整除时是大冒险，否则是真心话。

每轮开始后，当前参与名单保持不变：

- 非参与者发送 `/加入`，按申请顺序加入下一轮候选名单。
- 当前参与者发送 `/退出`，本轮仍必须报数并参与结算，下一轮才退出。
- 已申请下一轮退出的当前参与者不能撤销退出。
- 下一轮候选者可在下一轮开始前发送 `/退出` 取消申请。
- 接受下一轮加入时，按“当前人数 - 待退出人数 + 待加入人数”计算预计人数；预计达到 10 人后拒绝更多申请，不保留到更晚轮次。

有效轮结算后不会自动开始下一轮。任一当前参与者发送一次 `/继续` 后，系统先应用待退出名单，再按申请顺序应用待加入名单。应用后不足 3 人时，游戏直接结束；否则轮次加一、清空上一轮提交并进入新一轮 `collecting`。

若本轮少于三个不同的偏离值档位，本轮无效。机器人仍公开计算过程和无效原因，但不产生胜出者或受罚者；本轮提交全部清空，轮次编号、真心话或大冒险类型以及待加入和待退出名单均保持不变，系统立即重新收集同一轮数字，不要求发送 `/继续`。

任一当前参与者可以发送 `/结束游戏` 立即终止整场。未完成轮次不结算，下一轮候选者无权终止游戏。

## 私聊报数

每轮只接受当前参与者在与机器人一对一私聊房间中发送的 `/报数 整数`。整数范围为 `1–100`，每名玩家每次有效尝试的第一份合法提交立即锁定，之后不能修改。

提交成功、数字越界、格式错误、非本轮参与者以及重复提交都只回复原私聊房间。成功回复只确认本人已经报数，不透露其他玩家的数字或提交状态。

群内发送 `/报数` 不记入本轮，机器人只提示必须私聊提交。所有数字在全员完成前保密；最后一名玩家成功提交后，机器人在主群一次性公开本轮全部数字和结果。

## 精确计算与排名

设所有玩家数字之和为 `S`，人数为 `N`，则：

```text
平均值 A = S ÷ N
最终数 F = A × 0.8 = 4S ÷ 5N
玩家偏离值 D = |玩家数字 - F|
```

比较不能使用提前四舍五入的显示值。实现时可用共同分母 `5N`，以整数 `|5N × 玩家数字 - 4S|` 直接比较偏离值，避免浮点误差。

排名规则如下：

- 按偏离值从大到小排列。
- 相同精确偏离值共享同一档位，同档玩家按本轮参与名单顺序展示。
- 最小偏离档的全部玩家是胜出者。
- 第二大不同偏离档的全部玩家是受罚者。
- 少于三个不同偏离档时，本轮无效。

总和与人数显示为整数；平均值、最终数和偏离值使用常规四舍五入显示两位小数。排名始终依据完整精度，因此极少数情况下两个显示值相同，实际仍可能属于不同档位。

## 群内公布格式

有效轮使用固定三段式结构：

```text
第 N 轮 - 真心话/大冒险

1. 计算过程
玩家甲：29
玩家乙：5
……
总和：...
人数：...
平均值：...
最终数 F：...

2. 偏离值排序（从大到小）
玩家甲：...
玩家乙：...（第二大偏离 → 受罚者）
玩家丙：...（最小偏离 → 胜出者）
……

3. 最终游戏结果
胜出者：玩家名（数字）
受罚者：玩家名（数字）
本轮为真心话/大冒险轮，由胜出者出题并监督，受罚者必须完成对应惩罚。
```

多人并列胜出或受罚时完整列出所有人。无效轮保留前两段计算和排序，将第三段替换为“偏离值不足三个不同档位，本轮无效；请所有参与者重新私聊报数”，且不标记胜出者或受罚者。

## 无操作超时

管理端“玩法配置”增加“蹦蹦数字炸弹无操作超时（分钟）”字段，默认 `10`，允许范围为 `1–60`。保存后以最新配置和游戏的最后有效指令时间计算当前截止时间，对已经存在的游戏立即生效。

超时覆盖 `signup`、`collecting` 和 `waiting_continue` 三个阶段。以下指令仅在当前状态、身份和格式均合法，并实际改变游戏状态时刷新最后有效指令时间：

- `/加入`
- `/退出`
- 私聊 `/报数 整数`
- `/继续`
- `/结束游戏`

普通聊天、重复命令、越权命令、错误格式和群内 `/报数` 均不刷新计时。连续超过配置时长后，系统不结算、不处罚，向群内发送“蹦蹦数字炸弹长时间无人操作，本场已自动结束”，然后释放全部游戏占用。

## 私聊入站架构

现有系统已经能发现一对一房间并向其发送消息，但入站监听目前只接收主群消息。本功能采用正式扩展入站通道的方案：

- 入站消息契约和持久化记录增加消息来源类型与房间 ID，明确区分 `group` 和 `direct`。
- Browser Worker 继续定期发现一对一房间，并从核心服务取得当前轮需要监听的参与者集合。
- Socket Gateway 只为这些参与者的一对一房间加入监听和补拉历史，只转交以 `/报数` 开头的消息。
- 新创建的私聊房间通过现有房间发现和历史读取被补收；浏览器断线或重启后也通过历史补拉恢复未处理提交。
- 私聊 `/报数` 不进入普通群指令、AI 对话、玩家印象抽取或群聊活动统计。其他私聊内容不转交核心业务。
- 私聊确认或错误回复定向发送回入站私聊房间；最后一份报数触发的计算结果明确发送到主群。

平台消息 ID 继续作为全局入站幂等键。数据库另外约束同一游戏、同一轮次尝试、同一玩家最多一份有效提交，确保 Socket 实时事件、历史补拉或服务重试不会造成重复报数和重复结算。

## 持久化与并发

游戏数据需要持久化：

- 游戏状态、目标人数、当前轮次、当前尝试次数和最后有效指令时间；
- 当前参与者及其稳定展示顺序；
- 待加入和待退出状态；
- 每轮每次尝试的数字、精确偏离值档位和最终结果。

服务或 Browser Worker 重启后，未超时的游戏从数据库状态继续；重启期间已经超时的游戏在后台任务恢复时结束。已公布历史轮次保留，活动游戏结束时只释放活动唯一键，不删除历史结果。

创建、加入、退出、继续、结束以及最后一份报数必须接入现有玩法顺序锁并在事务中锁定活动游戏，防止并发消息造成超员、重复开轮、重复结算或同时占用多个游戏。

## 与现有系统的关系

“蹦蹦数字炸弹”的 `signup`、`collecting` 和 `waiting_continue` 都计入现有全局活动游戏判断：

- 存在其他多人游戏或进行中的随机事件时，拒绝创建本游戏。
- 本游戏活动期间，拒绝创建其他互斥游戏。
- 到点随机事件发现本游戏活动时，沿用现有逻辑将该次计划标记为跳过，不打断玩家。
- `/加入` 和 `/退出` 优先路由到当前活动游戏，保持现有共享指令语义。

玩法帮助和 AI 知识增加本游戏的规则说明与准确指令。机器人被问及玩法时只解释规则并引导玩家发送正确命令，不替玩家创建游戏或报数。

有效轮结束后，玩家记忆只记录参与、胜出、受罚以及本轮是真心话还是大冒险等事实，不记录数字、命令、计算过程或玩家围绕游戏发送的中间内容。无效轮不形成胜负事实。

## 错误反馈

- 未入职玩家创建或加入时，提示先发送 `/入职 名字`。
- 创建人数缺失、不是整数或不在 `3–10` 时，提示正确格式 `/蹦蹦数字炸弹 6`。
- 已有互斥游戏或随机事件时，提示当前有游戏或事件进行中。
- 群内 `/报数` 提示必须私聊；私聊报数错误只在私聊反馈。
- `/继续` 只在 `waiting_continue` 接受，报数未完成或无有效结算时拒绝。
- 非当前参与者不能 `/继续` 或 `/结束游戏`。
- 下一轮预计达到 10 人后，拒绝新的候选并提示下一轮人数已满。
- 应用下一轮人员变更后不足 3 人时，提示人数不足并结束整场。

所有固定回复继续接入现有回复模板体系，但本设计不增加惩罚题库、金币配置或其他未要求的管理项。

## 管理端

管理端玩法配置增加本游戏区块，提供规则摘要和无操作超时字段。本次只开放超时分钟数，不开放人数范围、数字范围、系数、轮次周期或消息格式配置。

核心内部 API 提供读取和保存本游戏设置的端点，使用现有管理员鉴权、并发版本和错误提示机制。保存成功后前端刷新展示服务端最终值。

## 验证

- 验证 `3–10` 人创建、报名、退出报名、发起者自动加入和满员自动开局。
- 验证只有已入职玩家能够创建或参加。
- 验证私聊房间发现、目标房间监听、历史补拉、同房间回复和主群结算路由。
- 验证其他私聊不进入 AI、记忆、普通指令或群聊活动统计。
- 验证群内 `/报数` 被拒绝，数字在全员完成前不公开，首次合法私聊提交锁定。
- 验证最后一份提交只结算一次，重复事件和断线补拉不会重复报数或公布。
- 验证总和、平均值、`F`、精确偏离排序和两位小数展示。
- 验证并列胜出、并列受罚、显示值相同但精确值不同，以及不足三个档位的无效轮重开。
- 验证第 1、2 轮真心话、第 3 轮大冒险并持续循环；无效轮不增加轮次。
- 验证 `/继续` 门控、下一轮候选顺序、待退出生效、人数上限和不足 3 人结束。
- 验证当前参与者主动结束，候选者和非参与者不能结束。
- 验证三个活动阶段的超时、合法指令续时、无效消息不续时及配置立即生效。
- 验证核心服务和 Browser Worker 重启后的恢复、超时清理和幂等处理。
- 验证与其他游戏互斥、随机事件跳过、玩法帮助以及事实型记忆边界。
- 验证管理端可在 `1–60` 分钟内读取和保存配置，生产前端端口 `18090` 可正常操作。
- 运行完整测试套件，确保现有游戏、随机事件、AI、记忆和消息发送行为不回归。
