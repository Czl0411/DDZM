# 甩锅炸弹游戏技术设计

## 目标与范围

实现 `rule.md` 第 12 节已经确认的单轮制群内小游戏，包括数据库迁移、核心状态机、群内指令、定时恢复、经济结算、回复模板、内部 API 和管理端页面。本期不调用 DeepSeek、不发送游戏私聊、不增加下一局候选队列，也不重构现有玩法。

实现基于 `codex/random-event-game-conflict-skip` 已完成的共享游戏门锁。甩锅游戏必须接入该门锁和统一活动游戏判断，保证它与随机事件、记忆考核对战、谁是卧底以及后续占用群级多人玩法锁的游戏不会并行创建。

## 已确认的补充规则

- `/结束游戏` 由当前甩锅对局中的任一参与者执行，不要求职位具备群内管理资格。非参与者不能终止对局。
- 职位的“多人小游戏发起次数”按北京时间自然日计算，只限制发送 `/甩锅游戏 人数` 的发起者；报名者不计次数，`-1` 表示不限。
- 只有报名局成功创建才消耗一次发起次数。参数错误、余额不足、玩法冲突、功能关闭或事故卡不可用等未创建状态不消耗；创建后即使报名超时或参与者提前结束也不返还次数。

## 技术方案

沿用现有核心仓储、命令分发、内部 API 和管理端的纵向结构实现完整功能。新增甩锅专用表和仓储方法，不建立独立微服务或新的领域框架。计时、余额变动和状态迁移都在数据库事务内完成，继续使用现有系统出站队列发送自动提示。

## 数据模型

### 全局配置

`blame_game_settings` 为主键固定为 `1` 的单例表，保存：

- `enabled`：总开关，默认开启。
- `signup_timeout_seconds`：报名超时，默认 `120` 秒。
- `turn_timeout_seconds`：单次操作时限，默认 `30` 秒。

`blame_game_duration_rules` 按 `player_count` 唯一保存 2–10 人的 `minimum_seconds` 和 `maximum_seconds`。迁移写入 `rule.md` 第 12.3 节的默认范围。两个秒数必须为正整数且最小值不能大于最大值。

### 事故卡

`blame_incident_cards` 保存事故名称、事故描述、JSON 关键词列表、启用状态和创建时间。事故名称必填；事故描述必填；关键词去除首尾空格后必须有 1–4 个且互不重复。已被对局使用的事故卡仍可编辑、停用或删除，因为对局只读取冻结快照。

### 对局与玩家

`blame_games` 保存：

- 状态 `signup`、`active`、`settled`、`dissolved` 或 `cancelled`。
- 非终态使用固定 `active_key="global"`；终态清空。唯一索引保证全局最多一场甩锅游戏。
- 发起者、目标人数、报名截止时间、创建时间、开局和结束时间。
- 事故卡来源 ID，以及事故名称、描述和全部关键词的冻结快照。
- 随机总时长、绝对引爆截止时间、当前操作截止时间。
- 当前持锅者、上一持锅者和最后一次已经自动公布的温度档。
- 失败者、结束原因和是否已经完成结算。

`blame_game_players` 以对局和用户唯一，保存报名顺序、开局后冻结的连续编号、玩家状态、保证金金额和保证金处理状态。报名顺序在退出后不复用；正式开局时按仍在场成员重新编号为 `1–N`。

`blame_game_transfers` 保存每次成功甩锅的原持锅者、目标持锅者、原始理由、规范化理由和时间。规范化理由在同一对局内唯一，数据库约束作为并发下的第二层保护。

`blame_game_daily_starts` 以用户和北京时间日期唯一，保存当天成功创建的报名局次数。事务锁定该行后再比较发起者当前职位的 `multiplayer_game_limit`。

## 状态机

正常路径为 `signup → active → settled`。

- `signup → dissolved`：报名超时，或人满准备开局时已没有可用事故卡；不产生胜负和余额变化。
- `signup → cancelled`：参与者发送 `/结束游戏`；不产生胜负。
- `active → cancelled`：参与者发送 `/结束游戏`；退还全部保证金。
- `active → settled`：全局引爆、当前持锅者操作超时或玩家主动退出；确定唯一失败者并结算。

所有终态迁移都清空 `active_key` 并记录结束时间。事务首先锁定活动对局；已经处于终态的重复任务直接返回现有结果，不再次退款、扣款或发奖。

## 创建、报名和开局

`/甩锅游戏 N` 只接受 2–10 人。创建事务按统一顺序获取共享游戏门锁，然后校验功能开关、发起者、职位当日次数、发起者余额、启用事故卡和其他互斥玩法。创建成功后发起者自动成为首名报名者，并把当日发起次数加一。

加入时要求玩家已入职、未重复报名，并且当前余额至少为本局 `N-1` 保证金。报名阶段的 `/退出甩锅` 删除或标记该报名成员退出，目标人数不变。

人满时在同一个对局事务内再次检查所有仍在场玩家的余额。余额不足者被移出并公开提示，对局回到继续等待状态。人数仍满时，从当前启用的事故卡中随机选择一张并冻结快照，按报名顺序冻结连续编号，统一暂扣每人 `N-1` 保证金，从对应人数范围内生成包含边界的随机总秒数，再随机选择第一位持锅者。没有可用事故卡时解散报名局。

游戏进行中收到 `/加入` 只返回“本局已开始，请结束后重新创建或报名”，不会加入当前游戏或保存候选人。

## 甩锅校验

仅当前持锅者可发送 `/甩锅 玩家编号 甩锅理由`。事务锁定活动对局后，先用消息的服务端接收时间比较全局和操作截止时间；已经到期则直接以当前持锅者为失败者结算。

未到期请求依次校验：

1. 目标编号存在、不是自己。
2. 三人及以上时目标不是上一位持锅者；两人局允许立即互甩。
3. 理由包含事故卡快照中的全部关键词。中文按连续原文匹配；英文字母忽略大小写。
4. 规范化理由未在本局成功使用。规范化依次执行首尾去空格、英文字母小写、连续空白合并为一个空格、删除 Unicode 标点类别字符。

失败校验不改变持锅者或任何截止时间。成功时记录转移，把原持锅者写为上一持锅者、目标写为当前持锅者，并把新操作截止时间设置为 `min(接收时间 + 单次操作时限, 全局引爆截止时间)`。全局引爆截止时间永不重置。

## 温度与定时任务

温度根据全局剩余比例计算：大于 70% 为“温热”；大于 40% 为“发烫”；大于 15% 为“滚烫”；其余为“即将爆炸”。开局和每次成功转移回复都包含当前温度。

甩锅定时任务与现有每日任务一起运行，负责：

- 解散报名超时的报名局。
- 在温度首次跨入新档时发送一次自动提示，并持久化最后公布档位。
- 在操作截止或全局引爆截止后，以当前持锅者为失败者结算。
- 服务恢复后按原绝对时间处理已经过期的状态。

若操作截止和全局截止都已到达，只执行一次相同结算。定时任务和用户请求竞争时，锁内以用户消息的服务端接收时间为判定依据；终态和结算标记保证后取得锁的一方不会重复处理。

## 经济结算

开局暂扣每人 `N-1`。正常结算时失败者保证金不退，每名赢家入账 `N`，等于退回自己的 `N-1` 保证金并净赚 `1`，整局净变化为零。进行中主动退出者直接成为失败者并触发同一结算。

参与者 `/结束游戏` 或其他无胜负取消路径退还全部已扣保证金。余额变动使用现有账本并带甩锅专用来源；锁定对局后根据玩家保证金状态更新，保证同一笔保证金只会结算或退款一次。对局终态、玩家保证金状态和余额流水在同一数据库事务提交。

## 与其他玩法的集成

甩锅创建使用共享游戏门锁，并加入统一活动游戏判断。活动甩锅局阻止随机事件手动或定时启动、记忆考核对战和谁是卧底创建；反向检查也阻止甩锅在这些玩法活动时创建。单人记忆考核和躲猫猫不占用群级多人玩法锁，行为保持现状。

`/加入` 的路由优先依据唯一活动多人玩法：甩锅报名局加入甩锅，甩锅进行中返回拒绝加入；不存在甩锅局时继续执行现有记忆对战或谁是卧底逻辑。`/结束游戏` 在活动甩锅局中只允许本局参与者终止，否则继续走现有谁是卧底行为。

随机事件指令门禁仍保持最高优先级；未被允许的甩锅指令不会绕过随机事件拦截。

## 回复模板与命令

新增 `/甩锅游戏`、`/甩锅`、`/退出甩锅` 命令定义和回复模板；扩展 `/加入`、`/结束游戏` 的玩法路由。模板覆盖创建、加入、报名退出、报名超时、开局、成功转移、缺少关键词、重复话术、目标无效、禁止回甩、非持锅者、四档温度、爆锅结算、主动退出、余额不足、事故卡不可用、玩法冲突、进行中拒绝加入、发起次数用尽和参与者终止。

所有玩法消息公开发送到群聊。关键词和话术校验为确定性本地逻辑，不调用 AI。

## 内部 API 与管理端

核心内部 API 提供：

- 读取和更新总开关、报名超时、操作时限及 2–10 人时长规则。
- 事故卡分页查询、新增、编辑、启停和删除。
- 查询当前报名或进行中的对局公开状态。
- 管理端强制结束当前对局。

管理端新增“甩锅游戏”页面，展示上述配置、事故卡管理和当前对局。对局状态展示目标人数、玩家与固定编号、事故卡、当前持锅者、温度和状态，不返回或渲染随机总秒数、引爆截止时间或操作截止时间。后台强制结束沿用无胜负取消和全额退款语义。配置写入继续使用现有管理端版本冲突保护。

## 验证策略

测试驱动实现，至少覆盖：

- 数据迁移、默认配置和 2–10 人时长规则。
- 创建、职位每日发起次数、报名、退出、超时、人满开局和余额不足移除。
- 事故卡快照、全部关键词、中英文匹配、完全重复话术和所有目标校验。
- 两人允许回甩、三人以上禁止立即回甩、有效转移不重置全局时间。
- 四档温度、跨档仅提示一次、操作超时、全局引爆和重启恢复。
- 保证金、主动退出、参与者终止退款、正常结算守恒和幂等性。
- 同一持锅者并发提交、甩锅与到期竞争，以及 PostgreSQL 下共享门锁竞争。
- 随机事件、记忆考核对战和谁是卧底双向互斥。
- 指令解析、回复模板、内部 API、管理端页面和强制结束。

完整测试通过后只提交本地实现并等待明确部署确认，不自动推送或部署。
