# 随机事件遇到游戏时跳过设计

**日期：** 2026-08-10  
**状态：** 待用户复核

## 目标

随机事件不得打断已经创建或正在进行的小游戏。定时随机事件到点时，如果群内存在任一活动游戏，本场随机事件直接标记为 `skipped`，不补发、不排队，也不阻止玩家继续完成当前游戏。

本次沿用既有随机事件“冲突场次跳过”语义，不新增随机事件队列、待触发状态、新游戏门禁或“随机事件即将到来”提示。

## 活动游戏定义

统一提供“当前是否有活动游戏”的仓库级判断，覆盖：

- 单人或双人记忆考核：`active_key` 仍存在的全部状态，包括展示题目、等待答案、等待 `/继续` 或 `/收手`、等待对手和对战进行中；
- 摸鱼躲猫猫：任意玩家存在 `selecting` 状态的对局；
- 谁是卧底：会话仍持有活动键的全部状态，包括报名、发牌、发言、投票、并列补充发言和等待下一局。

已结束、失败、结算、取消或过期记录不算活动游戏。

甩锅游戏尚未实现，本次不添加占位代码；实现时必须接入同一活动游戏判断。

## 定时随机事件

后台任务按计划时间查询到期的 `pending` 场次，并按 `scheduled_at` 顺序处理：

1. 若已有随机事件处于报名或进行状态，沿用现有逻辑，将本场标记为 `skipped`。
2. 若没有活动随机事件，但存在任一活动游戏，将本场标记为 `skipped`。
3. 若不存在任何冲突，正常创建随机事件并发送报名公告。

被跳过的场次不生成 `RandomEventRecord`，不发送报名、提醒或警告消息，也不修改当前游戏的状态、次数、余额或奖励。

若同一次后台任务处理多条已到期计划，最早一场成功启动后，后续场次会因为已有活动随机事件而按现有规则标记为 `skipped`。

## 管理员立即触发

管理员对 `pending` 场次执行“立即触发”时：

- 已有随机事件则继续返回现有的“当前已有进行中的随机事件”错误；
- 存在其他活动游戏则拒绝操作并返回“当前有游戏进行中”；
- 没有冲突则立即触发。

因活动游戏而拒绝时，计划仍保持 `pending`，不会提前标记为 `skipped`。到达原定时间后，由定时任务根据当时状态决定正常触发或跳过。

## 游戏流程与事务一致性

随机事件冲突检查只作用于“创建新游戏”和“触发随机事件”的边界。已经创建的游戏仍允许：

- 玩家加入既有报名局或等待对手局；
- 作答、选址、投票和其他正常推进操作；
- 主动退出、超时处理、管理员终止和结算。

所有新游戏创建入口与随机事件触发入口共用同一个数据库事务门闩。事务先取得门闩，再检查活动状态并创建记录，避免游戏创建与随机事件触发在并发请求中同时通过检查。

门闩复用现有随机事件单例配置记录的行锁，不新增数据库表或迁移。既有游戏的加入和后续操作不需要取得该门闩。

## 管理端与文案

- 今日随机事件列表继续使用既有 `skipped` 状态展示，不新增排队状态或跳过原因字段。
- 定时跳过不向群内发送新提示。
- 管理员立即触发失败沿用管理端现有错误提示机制，展示“当前有游戏进行中”。
- 不新增可配置群回复文案。

## 测试

仓库测试覆盖：

- 活动单人记忆考核导致到点随机事件 `skipped`；
- 活动双人记忆考核导致到点随机事件 `skipped`；
- 任一玩家的 `selecting` 躲猫猫导致到点随机事件 `skipped`；
- 谁是卧底各活动阶段导致到点随机事件 `skipped`；
- 已结束、失败、结算、取消和过期记录不阻塞随机事件；
- 定时跳过不创建随机事件、不发送报名公告、不改变现有游戏；
- 多条同时到期计划只启动最早一场，其余按现有规则跳过；
- 管理员立即触发遇到各类活动游戏时返回“当前有游戏进行中”，且计划保持 `pending`；
- 无活动游戏时，定时与手动触发仍正常工作；
- 并发创建游戏与触发随机事件时只允许一方成功占用活动时段。

命令和管理端测试验证错误能够透传并按现有方式展示。完整测试通过后先向用户汇报，得到再次确认后才部署正式环境。

## 不在本次范围

- 随机事件 FIFO 队列或补发机制；
- 待触发随机事件阻止新游戏创建；
- “随机事件即将到来，稍等一会”可配置提示；
- 修改随机事件固定时间、报名超时、提醒间隔或场景抽取规则；
- 甩锅游戏实现。
