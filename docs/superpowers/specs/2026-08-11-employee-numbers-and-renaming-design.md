# 员工工号与修改名称设计

## 目标

为每位员工分配永久、唯一的数字工号，解决员工重名时无法精确定位的问题；同时新增员工自助修改昵称的指令。工号只在确有辨识需要的场景展示，普通群聊和游戏消息继续使用简洁昵称。

## 工号规则

- `users` 表新增唯一、非空的整数工号字段 `employee_number`。
- 工号从 `1` 开始，展示时至少补齐四位：`#0001`、`#0023`；超过四位后自然显示，例如 `#10000`。
- 工号一经分配永久不变，不回收、不重排。
- 历史员工按照 `joined_at` 从早到晚依次补齐；入职时间相同时，以用户 UUID 升序作为稳定的第二排序条件。
- 新员工永远取得当前计数器中的下一个号码。
- 使用独立的单行工号计数器表。创建员工时锁定计数器行，取号后递增，确保 PostgreSQL 并发入职不会得到重复工号；SQLite 测试环境沿用同一数据模型。

## 工号展示范围

工号不是昵称的一部分，多数消息不展示工号。

仅在以下位置展示：

- `/入职` 成功回复中单独提示一次：`你的工号：#0001`。
- `/我` 回复中单独显示一行：`工号：#0001`。
- 管理端员工列表在昵称旁显示工号，并允许按工号搜索。
- 员工昵称发生重名、管理指令无法唯一定位时，回复中列出候选人的昵称和工号，例如：`小明 #0001、小明 #0023`。

以下位置继续只显示普通昵称：

- `/余额`、`/我的物品`。
- `/修改名称` 的成功回复。
- `/发奖金` 的成功通知。
- 部门与晋升申请、审批和普通通知。
- 随机事件、谁是卧底、记忆考核、甩锅游戏、蹦蹦数字炸弹等游戏消息。
- 红包、打卡和其他群聊播报。

## 工号定位

需要指定单个员工的 `/发奖金` 支持以下形式：

- `/发奖金 #0001 5`：按工号精确定位员工。
- `/发奖金 小明 5`：保留纯昵称兼容；昵称唯一时正常执行。
- 纯昵称匹配到多名员工时拒绝执行，列出候选员工及其工号，并提示改用工号重试。
- `/发奖金 全部 5`：原有全员发放逻辑不变。

工号输入接受 `#` 后一位或多位十进制数字，前导零不影响识别；`#1` 与 `#0001` 指向同一员工。不存在的工号返回员工不存在，不回退为昵称搜索。

## 修改名称指令

新增 `/修改名称 新名称`，规则如下：

- 只修改指令发送者自己的昵称。
- 发送者必须已经入职。
- 免费且不限次数。
- 以指令名后的全部文本作为新名称，去除首尾空格后长度必须为 1–64 个字符。
- 允许与其他员工重名，也允许名称中包含 `#` 和数字。
- 修改昵称不会改变工号、余额、职位、部门、游戏数据或 AI 记忆。
- 修改完成后的新消息使用新昵称；已经保存的历史快照保留发生时的旧名称。
- 成功回复为：`名称已修改：旧名称 → 新名称。`
- 新名称与当前名称完全一致时不写数据库，回复当前名称未变化。

新增指令及所有回复场景进入现有指令库和可编辑回复模板体系。至少包含：使用方式、未入职、名称无效、名称未变化和修改成功。

## API 与管理端

- 核心员工响应增加整数 `employee_number`。
- 管理端员工列表显示格式化工号，但 API 保持返回原始整数，格式化由展示层完成。
- 管理端员工搜索同时匹配昵称、格式化工号和纯数字工号。
- 现有以平台用户 ID 执行的 AI 记忆和董事会管理操作不改变目标标识，只增加可见工号帮助管理员核对身份。

## 数据迁移

迁移按以下顺序执行：

1. 为 `users` 增加暂时可空的 `employee_number`。
2. 按 `joined_at ASC, id ASC` 为历史员工写入从 `1` 开始的连续工号。
3. 增加唯一约束并把字段改为非空。
4. 创建工号计数器表，并将下一工号初始化为历史最大工号加一；没有历史员工时初始化为 `1`。

迁移不得修改员工昵称、平台 ID、余额、组织关系或历史业务记录。

## 错误处理

- 无效的工号格式作为普通昵称处理；只有完整匹配 `#` 加十进制数字时才按工号查询。
- 合法但不存在的工号返回员工不存在。
- 重名纯昵称不选择“第一个”员工，必须拒绝并给出候选工号。
- 修改名称缺少参数或超过 64 个字符时不写数据库，返回可编辑的名称无效回复。

## 验证标准

- 迁移测试证明历史员工严格按入职时间和 UUID 获得稳定工号，计数器从下一个号码继续。
- 数据库约束测试证明工号唯一且非空。
- 仓储测试证明新员工连续取号、工号永久不变、改名不影响其他员工资料。
- 指令测试覆盖 `/修改名称` 的成功、未入职、参数无效、未变化和允许重名。
- `/发奖金` 测试覆盖纯工号、带前导零工号、唯一昵称、重名昵称候选提示、不存在工号和 `全部`。
- API 与管理端测试证明员工列表返回、显示并搜索工号。
- 回归测试证明游戏、随机事件、红包及普通通知没有被统一追加工号。

## 不在本次范围

- 不允许管理员修改或重新分配工号。
- 不给历史游戏、事件和申请快照补写工号。
- 不把工号追加到平台昵称或每一条群聊消息中。
- 不增加修改名称的费用、次数限制或冷却时间。
