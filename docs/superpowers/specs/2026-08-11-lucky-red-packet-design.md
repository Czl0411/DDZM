# 随机运气红包设计

## 目标

新增一个独立于现有游戏的群内资产玩法。员工使用 `/发红包 人数 总金额` 从自己的余额中创建随机运气红包，其他员工使用 `/抢红包` 领取真实摸鱼币。红包抢完后，系统公布全部领取结果以及唯一的手气最佳和手气最差。

本功能必须保证：

- 红包总额与所有预生成份额之和完全一致；
- 最多出现一份金额为 `0` 的空包；
- 最大金额和最小金额都只有一份；
- 余额扣除、领取和退款均可追踪且不会重复执行；
- 红包不占用现有“当前游戏”，也不阻塞随机事件或小游戏。

## 群指令

### `/发红包 人数 总金额`

- 仅已入职员工可在群聊中使用。
- 人数只接受 `2–50` 的半角整数。
- 总金额只接受半角整数，范围为 `人数–99999`。
- 总金额表示整个红包的摸鱼币总额，不是每人金额。
- 发起者可以领取自己创建的红包。
- 每位员工按北京时间自然日最多成功创建 `5` 个红包。
- 只有创建成功才消耗一次每日次数；参数错误、余额不足或已有活动红包时不消耗。
- 同一时间全局只允许一个未结束红包。
- 私聊使用时不产生资金变动，只提示回群操作。

示例：

```text
/发红包 5 5
```

表示创建一个由最多 5 名员工瓜分、总额为 5 摸鱼币的红包。

### `/抢红包`

- 仅已入职员工可在群聊中使用。
- 每名员工对同一个红包最多成功领取一次。
- 按首次成功处理顺序领取下一份预生成金额。
- 金额为 `0` 的空包同样占用一个领取名额并生成领取记录，但不增加余额。
- 私聊使用时不产生资金变动，只提示回群操作。

## 生命周期与消息

### 创建

创建成功时，系统在一个数据库事务中：

1. 校验员工、参数、每日次数、活动红包与余额；
2. 从发起者余额一次性扣除红包总额；
3. 增加发起者当日成功创建次数；
4. 生成并保存全部随机份额；
5. 将红包标记为待领取，并记录过期时间。

群内通知展示发起者、红包人数、总金额、有效时间，并引导员工发送 `/抢红包`。

### 领取

每次成功领取后立即入账并公开通知：

```text
张三抢到 1 摸鱼币，剩余 3/5 份。
```

领取者是发起者本人时规则不变：红包创建时先扣除总额，领取时再按实际份额入账。

### 抢完

最后一份被领取后，红包立即完成。系统在群里按领取顺序公布所有员工及金额，并标注：

- 手气最佳：唯一最大金额的领取者；
- 手气最差：唯一最小金额的领取者；
- 最小金额为 `0` 时额外标注“空包”。

最后一位领取者的即时通知和整包统计是两条独立消息。

### 过期

- 默认有效期为 `10` 分钟。
- 到期时关闭红包，不能再领取。
- 已领取金额不撤回。
- 所有未领取份额的总金额原路退回发起者。
- 群内通知已领取人数、总人数和退款金额。
- 未抢完的红包不评选手气最佳与手气最差。
- 定时任务、创建新红包和抢红包操作都可以触发过期检查，但同一红包只能退款和通知一次。
- 在过期边界时刻，过期处理优先于领取。

## 随机份额算法

### 空包判定

空包概率默认 `5%`，管理端可配置为 `0%–30%`。

以下场景为了满足整数金额、最多一个空包以及唯一最大值和最小值，必须强制生成空包：

- `2` 人且总金额为 `2`；
- `3` 人以上且总金额小于 `人数 × 2`。

强制空包不受配置概率影响。其他可生成全正数唯一极值的场景，才按配置概率决定是否出现空包。

### 基础份额

- 有空包时，先构造 `0、1……、1、2`，基础总额等于人数；
- 无空包且人数为 `2` 时，先构造 `1、2`，基础总额为 `3`；
- 无空包且人数不少于 `3` 时，先构造 `1、2……、2、3`，基础总额等于 `人数 × 2`。

基础份额已经保证最小值和最大值各自唯一。

### 剩余金额

将总金额减去基础总额，逐枚随机分配剩余摸鱼币：

- 空包槽位不再增加；
- 唯一最小槽位不再增加；
- 当前最大槽位始终可以增加；
- 中间槽位只有在增加后仍严格小于当前最大值时才可增加。

每次从当时符合条件的槽位中随机选择一个。完成后再次校验份额数量、总额、零值数量以及最大值和最小值唯一性；校验失败则整个创建事务失败，不扣币也不消耗次数。

最后使用系统随机源打乱全部份额顺序后持久化。随机源需要支持测试注入，但不承诺在所有合法整数拆分之间形成均匀概率分布。

示例：

- `5 人 5 币` 必须生成打乱后的 `0、1、1、1、2`；
- `5 人 9 币` 仍必须生成一份空包；
- `5 人 10 币` 可以生成全正数份额，默认按 `5%` 概率决定是否改为空包结构。

## 数据与账务

### 红包记录

红包记录至少保存：

- 发起者；
- 目标人数；
- 总金额；
- 状态：待领取、已抢完、已过期；
- 创建时间、过期时间、完成时间；
- 是否包含空包；
- 退款金额与退款时间。

### 份额记录

每个预生成份额独立保存：

- 所属红包；
- 随机顺序；
- 金额；
- 领取者与领取时间。

数据库约束保证同一红包的份额顺序唯一，同一员工对同一红包最多领取一次。

### 每日次数

使用独立的每日发红包计数记录，按发起者和北京时间日期唯一。成功创建时在红包创建事务内递增。

### 余额流水

流水来源明确区分：

- `red_packet_fund`：创建红包时从发起者扣除总额；
- `red_packet_claim`：领取正数份额时增加领取者余额；
- `red_packet_refund`：红包过期时退还未领取总额。

空包只生成领取记录，不写金额为零的余额流水。

## 并发与幂等

- 创建时锁定活动红包判定所依赖的数据，保证不会并发创建两个活动红包。
- 领取时锁定活动红包和下一份未领取份额，防止两人领取同一份。
- 领取记录的数据库唯一约束防止同一员工重复领取。
- 最后一份领取、红包状态变更和领取入账在同一事务完成。
- 过期状态变更、退款流水和通知入队在同一事务完成。
- 继续复用平台消息 ID 的入站幂等机制，重复投递同一条 `/发红包` 或 `/抢红包` 不会重复扣款或领取。

## 管理端与指令库

在“玩法配置 → 小游戏”增加随机运气红包配置：

- 过期时间：`1–60` 分钟，默认 `10`；
- 空包概率：`0%–30%`，默认 `5%`。

每日次数固定为 `5`，人数和金额范围固定为本设计规定值，不增加额外配置。

指令库增加：

- `/发红包 人数 总金额`；
- `/抢红包`。

两个指令均支持启停。创建、领取、抢完、过期和各类拒绝回复都纳入现有可编辑回复模板体系。若活动红包期间 `/抢红包` 被管理员停用，红包仍会按正常过期规则退款。

## 拒绝场景

以下场景不扣币、不消耗次数，也不新增领取记录：

- 未入职；
- 私聊执行资金指令；
- 参数缺失、非半角整数或超出范围；
- 发起者余额不足；
- 发起者当日已成功创建 5 次；
- 已有未结束红包；
- 当前没有可抢红包；
- 红包已经过期或抢完；
- 当前员工已经领取过该红包。

## 测试与验收

### 随机性质

- 覆盖人数 `2`、`3`、`50` 和金额上下边界；
- 覆盖强制空包、配置空包和无空包；
- 对生成结果验证份额数、总额、非负整数、最多一个零、唯一最大值和唯一最小值；
- 验证打乱和随机分配可通过注入随机源稳定测试。

### 账务与状态

- 创建成功全额扣款并消耗一次每日次数；
- 创建事务任一步骤失败时全部回滚；
- 正数份额正确入账，空包不增加余额；
- 发起者可以领取自己的红包；
- 抢完时完整统计正确；
- 过期只退未领取金额，退款与通知幂等；
- 北京时间跨日后每日次数恢复。

### 并发与消息

- 并发创建只能成功一个红包；
- 并发抢取不会重复领取同一份；
- 同一员工并发重复抢取只成功一次；
- 并发领取最后一份只结算和通知一次；
- 重复平台消息不会重复产生余额变化。

### 管理与回归

- 管理端可以读取和保存过期时间与空包概率；
- 指令库显示准确语法并支持启停；
- 所有红包回复模板可读取、编辑和恢复默认值；
- 完整自动化测试通过；
- 正式环境发布后验证核心、管理端、Browser Worker、AI Worker 与 AI Memory Worker 状态，确认监听状态和消息队列正常。
