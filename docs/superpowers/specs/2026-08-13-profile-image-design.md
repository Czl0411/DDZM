# 档案形象设计

## 目标与范围

在现有个人档案功能上增加“档案形象”。玩家回复群聊中的一张图片并发送 `/编辑档案形象`，系统保存被引用图片的地址；发送 `/我的档案` 时，机器人先发送文字个人介绍，再在已经设置形象时单独发送形象图片。

档案形象依附于文字个人档案，不是独立档案。未填写文字档案的玩家不能设置形象；管理员清空文字档案时必须同时清除已有形象。

本功能包括：群聊引用图片识别、玩家设置与查看、图片出站发送、后台本地图片上传、后台预览/替换/清除、持久化上传任务和相应测试。不改变现有 AI 记忆提取逻辑，也不把图片内容交给 AI 分析。

## 玩家指令

### `/编辑档案形象`

玩家必须使用回复功能引用一条图片消息，并发送完整指令 `/编辑档案形象`。

处理顺序如下：

1. 检查发送者是否已经入职；未入职时拒绝。
2. 检查玩家是否已经填写文字个人档案；未填写时提示“请先完成个人档案，再设置档案形象。”
3. 检查指令是否引用图片，且引用中存在有效图片 URL；否则提示玩家回复一张图片后重新发送指令。
4. 检查新图片 URL 是否与当前档案形象一致；一致时提示没有变化，不扣除任何资源。
5. 使用现有个人档案费用配置检查玩家余额和全公司共享公共人力。
6. 在同一数据库事务内扣除当前配置的编辑费用、扣除 1 点公共人力并保存图片 URL。任何一步失败时全部回滚。

编辑档案形象与编辑文字档案共用现有 `edit_cost` 和 `shared_labor` 配置，不新增独立费用。余额不足或公共人力不足时不修改形象，也不发生部分扣除。

### `/我的档案`

- 未入职或未填写文字个人档案时沿用现有回复。
- 已填写文字档案时，第一条消息发送文字个人介绍。
- 已设置档案形象时，第二条消息发送图片；未设置时不发送第二条，也不额外提示。
- 两条消息使用同一持久化出站队列，并按创建顺序发送。

## 入站图片引用

群聊平台的图片消息内容结构为：

```json
{
  "type": "image",
  "url": "图片地址",
  "alt": "image",
  "width": 1254,
  "height": 1254,
  "blurhash": "..."
}
```

回复图片的文字消息在 `content.reference` 中包含原消息：

```json
{
  "type": "text",
  "text": "/编辑档案形象",
  "reference": {
    "id": "原图片消息 ID",
    "sentBy": "原图片发送者 ID",
    "content": {
      "type": "image",
      "url": "图片地址",
      "alt": "image",
      "width": 1254,
      "height": 1254,
      "blurhash": "..."
    }
  }
}
```

Browser Worker 的接收层需要保留实现所需的引用字段：原消息 ID、原发送者 ID、内容类型、图片 URL、替代文本、宽高和 blurhash。核心层只使用引用类型和 URL 执行本指令。普通文本消息和现有记忆提取仍只消费玩家实际发送的文字，不把引用内容作为玩家证据。

## 数据模型与事务

员工记录增加可空的档案形象 URL 字段，历史员工默认未设置。文字档案和形象仍属于同一员工档案。

玩家设置形象的数据库事务必须锁定发送者员工记录和个人档案设置记录，并在锁内重新检查：

- 员工仍然存在；
- 文字档案仍非空；
- 图片尚未成为当前形象；
- 余额足够；
- 公共人力大于零。

检查通过后再同时扣费、扣公共人力并更新形象 URL。

管理员清空文字档案时，在同一事务内把形象 URL 设为空。管理员单独替换或清除形象不扣玩家余额，也不消耗公共人力。

## 图片出站发送

现有出站消息扩展为文本和图片两种内容类型：

- 文本继续保存和发送现有 `text` 字段；
- 图片保存图片 URL 和可选替代文本，并通过 Socket `message:send` 发送 `{type: "image", url, alt}`；
- 现有租约、失败重试、发送确认和平台消息 ID 回写机制同时适用于图片；
- 兼容所有现有文本出站记录和发送逻辑。

`/我的档案` 创建一条文字出站记录，并在存在形象时紧接着创建一条图片出站记录。两条记录在同一处理流程中按创建顺序入队，不重复扣费；图片发送失败只进入出站重试，不影响已经保存的档案。

## 后台员工档案管理

员工档案弹窗增加：

- 当前档案形象预览；
- 本地图片选择；
- 上传并替换；
- 清除形象；
- 上传任务状态和失败原因。

允许 JPEG、PNG、WebP，单图不超过 10 MB。前端在提交前校验类型和大小，服务端再次校验，不能只依赖浏览器校验。

管理员上传、替换、清除或因清空文字档案而清除形象，均不扣员工余额、不消耗公共人力。

## 后台本地图片上传任务

后台不能直接持有群聊平台登录态。管理员提交本地文件后，管理服务创建持久化图片上传任务，由 Browser Worker 使用现有登录会话执行：

1. 管理服务接收并校验文件，保存到仅供任务使用的受控临时目录。
2. 创建任务并记录员工、临时文件、原始文件名、MIME 类型、档案版本和状态。
3. Browser Worker 使用现有任务租约领取任务。
4. Worker 调用 `chatroom.uploadImage`，表单字段为 `file` 和目标 `chatroomId`。
5. 平台返回图片 URL 后，核心服务校验档案版本，再保存 URL。
6. 完成或失败后清理临时文件；失败时保留原档案形象并记录简短失败原因。

任务状态为：

- `pending`：等待 Worker；
- `processing`：Worker 已领取；
- `completed`：上传并替换成功；
- `failed`：上传失败，保留旧图，可由管理员重新提交；
- `superseded`：档案版本已变化，旧任务结果不得覆盖新操作。

Worker 或服务重启后，过期租约任务可重新领取。数据库只保存任务元数据和最终 URL，不保存图片二进制。

## 并发与防止旧任务覆盖

每次后台上传任务绑定创建时的档案版本。如果管理员在上传期间执行了新的上传、清除形象或清空文字档案，档案版本发生变化。旧任务即使随后上传成功，也必须标记为 `superseded`，不能回写 URL。

清除形象和清空文字档案是立即生效的同步操作。清空文字档案还会让所有尚未完成的对应上传任务失去回写资格。

## 回复模板与管理配置

`/编辑档案形象` 加入指令库、帮助和可配置回复模板，至少包括：

- 使用方式错误或未回复图片；
- 未入职；
- 尚未填写文字档案；
- 形象未变化；
- 余额不足；
- 公共人力不足；
- 更新成功。

余额不足回复继续显示当前配置的编辑费用和货币名称。公共人力不足不向玩家公开剩余数量。

## 错误处理

- 引用缺失、引用不是图片或图片 URL 无效：拒绝指令，不扣资源。
- 玩家设置过程中数据库写入失败：事务整体回滚。
- 后台文件类型或大小不合法：不创建任务。
- Worker 上传失败：任务标记失败、删除临时文件、保留旧形象。
- Worker 上传成功但档案版本已变化：任务标记为已过期，不覆盖当前形象。
- `/我的档案` 图片发送失败：沿用出站重试，不重复生成文字消息或扣除资源。

## 测试与验收

自动化测试至少覆盖：

1. 入站层保留图片引用结构，普通文本接收保持兼容。
2. 回复图片可以设置形象；未引用图片、未入职、未填写文字档案均被拒绝。
3. 成功更新原子扣除个人余额和 1 点公共人力；余额或人力不足不发生部分修改。
4. 相同图片不扣资源。
5. `/我的档案` 始终先发送文字；存在形象时第二条发送图片，不存在时只有文字。
6. 图片出站使用正确的平台结构，并具备发送确认与失败重试。
7. 后台可预览、上传替换和清除形象，且不扣玩家资源。
8. 后台清空文字档案同时清除形象。
9. 非法类型和超过 10 MB 的文件被拒绝。
10. Worker 可领取、完成、失败重试上传任务；重启后过期租约可恢复。
11. 旧上传任务不会覆盖较新的上传、清除或文字档案清空。
12. 数据库迁移为历史员工提供空形象，现有功能和数据保持兼容。
13. 全量测试、迁移升级与降级测试通过。

## 不在本次范围

- 不分析或识别图片内容。
- 不把档案形象加入 AI 对话上下文或记忆提取。
- 不允许未填写文字档案的玩家单独设置或展示形象。
- 不增加独立的档案形象费用或公共人力配置。
- 不自动删除群聊平台上已经上传但因任务过期而未采用的远端图片。
- 实现完成后不自动部署；先汇报代码和验证结果，等待用户确认。
