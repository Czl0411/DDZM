# 按会话并发发送与回复定位设计

## 目标

解除不同会话之间的出站消息互相阻塞，同时保证同一会话内的消息顺序、幂等确认和引用关系不变。凡由一条玩家消息直接触发的机器人回复，都在群聊平台显示为对该原消息的引用回复。

## 并发模型

- 出站发送采用有界并发，默认最多 4 个发送任务同时运行。
- 发送键为实际目标会话：群消息使用目标群聊 ID，私聊使用 `destination_chatroom_id`。
- 同一发送键任一时刻最多租用并发送一条消息；不同发送键可以并发。
- 同一入站产生的多段回复继续按 `reply_index` 严格发送，不得并发或乱序。
- 较早消息处于 `pending` 或 `leased` 时，后续同会话消息不得被领取。
- 某一路失败只结束该发送键当前任务并按现有租约规则重试，不停止其他会话。
- 并发数进入 Worker 环境配置，默认 4，最小 1，最大 16。

## 回复定位

- `inbound_message_id` 非空的出站消息保存原平台消息的引用快照：平台消息 ID、发送者平台 ID、内容类型及原文字内容。
- Socket 文本与图片消息在 `content.reference` 中发送该快照，结构为：

```json
{
  "type": "text",
  "text": "机器人回复",
  "reference": {
    "id": "原平台消息 ID",
    "sentBy": "原发送者平台 ID",
    "content": {"type": "text", "text": "原文"}
  }
}
```

- 一条玩家消息触发多段回复时，每一段都引用同一条原消息。
- 定时提醒、自动结算、系统广播及后台主动通知等 `inbound_message_id` 为空的消息不增加引用。
- 私聊回复同样引用对应的私聊原消息。
- 引用快照在入队时生成，不在发送时重新查询可变数据。

## 长消息

现有官方 Bot API 请求体只包含 `chatroom_id` 和纯文本 `content`，没有已经验证的引用参数。需要回复定位的群消息不得走该接口；超过 Socket 限制时沿用现有切片算法，每个分片分别引用原消息并按序发送。没有原消息引用的系统长消息仍可继续使用官方 Bot API。

## Socket 并发安全

- `AikdaSocketGateway` 对已加入房间集合及连接重建状态加锁。
- 每个发送键使用独立串行锁；底层 Socket ACK 可由不同发送键并行等待。
- 连接失效或认证失败仍由 Worker 统一关闭并恢复；关闭过程只执行一次。
- 出站使用 UUID 作为平台消息 ID，租约确认和重试幂等规则不变。

## 验收

1. 同一会话的两条消息严格按创建顺序发送。
2. 不同私聊会话的慢 ACK 可以重叠等待，总耗时显著低于串行总和。
3. 一路发送失败不阻止另一路成功确认。
4. 同一入站的所有文本分片和图片均包含正确原消息引用。
5. 定时/系统出站不包含引用。
6. 带引用的长消息走 Socket 分片；无引用的系统长消息仍可走 Bot API。
7. Worker 重启后租约恢复，不重复确认或跳过同会话早期消息。
