# Browser Worker 消息延迟修复设计

## 背景与根因

正式环境已登记 52 个私聊房间。Browser Worker 每 30 秒先通过
`discover_direct_chats()` 逐个读取全部私聊历史，再通过
`reconcile_history()` 读取群聊及全部私聊历史。单轮约 105 次请求，线上实测约
54 秒。

这段同步位于出站消息领取之前。Core 通常可在 1 秒内生成普通指令回复，
DeepSeek 通常在 4 到 9 秒内生成回复，但出站消息必须等待整轮历史同步结束，
导致平均约 36 秒、P95 约 70 秒的额外发送延迟。

## 目标

- 实时入站 Socket 监听和现有私聊投稿、私聊游戏流程保持不变。
- 已生成的出站消息优先领取和发送，不等待全量历史同步。
- 每次 Worker 主循环最多执行一个历史房间请求，将同步造成的连续阻塞限制在
  单个请求耗时内。
- 启动或 Socket 重连后仍能逐步补偿群聊和已知私聊中的漏收消息。
- 新私聊仍能被发现、登记和加入 Socket 监听范围。
- 不在非所有者线程调用 Playwright 或执行 Socket 重连。

## 方案比较

### 方案一：仅把发送移动到同步之前

改动最小，但同步期间新生成的消息仍可能等待约 54 秒，只能降低部分延迟，
不能消除根因。

### 方案二：主线程内分片同步（采用）

保留 Browser Worker 对 Playwright 和 Socket 的线程所有权，把私聊发现和历史
补偿改为可恢复的分片任务。每轮先处理实时消息和出站，再执行至多一个历史
房间请求。实现范围局部，且不会引入跨线程浏览器访问。

### 方案三：独立同步进程

隔离最彻底，但需要新的服务、浏览器连接和协调协议，超出本次故障修复范围。

## 设计

### Worker 主循环顺序

Browser Worker 在认证和监听状态同步后按以下顺序工作：

1. 读取并分派 Socket 已缓存的实时入站消息。
2. 执行必要的定时任务与撤回任务。
3. 领取并异步发送出站消息。
4. 在主线程末尾执行一个私聊维护分片。

因此，即使维护分片中的平台请求变慢，也不会阻止本轮已经存在的出站消息被
领取。维护分片最多包含一个历史房间请求，下一轮出站最多只会等待一个平台
请求，而不是等待全部房间。

### 私聊维护状态

`AikdaSocketGateway` 保存两类有界队列：

- **发现队列**：周期性调用一次 `chat.listAll` 后，只把尚未登记的单聊房间放入
  队列。每个维护分片最多读取其中一个房间的历史，以确定对方用户并返回映射。
- **补偿队列**：首次连接或重连后，将群聊和当前已登记私聊加入队列。每个维护
  分片最多读取一个房间，交给现有去重逻辑接收漏掉的文本消息。

未完成的队列不会被新的周期刷新覆盖。已知私聊不会在每个发现周期重复读取
历史。Socket 断开或重连时清空旧的加入状态，并重新建立补偿队列。

发现和补偿共用单个分片预算：一次主循环最多产生一个
`chatroom.getMessages` 请求。`chat.listAll` 刷新本身也作为一个独立分片，不与
历史读取叠加。

### 数据与兼容性

- 不修改数据库结构或环境变量。
- `direct_chats` 仍是私聊用户与房间映射的权威存储。
- 现有 Socket 消息 ID 去重、私聊入站先登记映射、出站顺序和租约逻辑保持不变。
- 现有管理端监听开关、人工登录和浏览器重启行为保持不变。

### 错误处理

- 单个发现或补偿分片失败时记录错误并结束本轮维护，不影响出站发送、监听状态
  或 Worker 进程。
- Socket 认证丢失继续沿用现有恢复流程。
- 未完成队列在下一轮继续，避免一次失败后重新扫描全部房间。

## 测试与验收

- 回归测试证明：维护步骤被阻塞时，本轮出站消息仍已被领取并开始发送。
- 单元测试证明：一个维护步骤最多读取一个历史房间。
- 单元测试证明：已知私聊不会被发现流程重复读取历史。
- 单元测试证明：启动或重连后的补偿按房间逐步完成，且消息仍按 ID 去重。
- 运行全部测试，确保 Browser Worker、私聊投稿、谁是卧底发牌和蹦蹦数字炸弹
  私聊报数没有回归。
- 部署后用数据库时间戳验证普通指令的“回复创建到发送完成”P95 显著低于故障期
  的约 70 秒，并确认 Worker 无新增重启或认证丢失。

## 非目标

- 不调整 DeepSeek 模型、超时或上下文长度。
- 不修改群聊平台接口协议。
- 不新增独立系统服务或消息中间件。
- 不清理历史私聊映射。
