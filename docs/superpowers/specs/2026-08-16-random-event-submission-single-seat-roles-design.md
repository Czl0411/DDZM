# 随机事件投稿单席身份设计

## 目标

简化随机事件投稿中的身份录入。投稿者确定事件参加人数后，只需逐个发送身份名称；每个身份固定占 1 个席位，不再单独询问身份人数。身份数量达到参加人数时，向导自动进入事件模板环节。

本次只调整玩家投稿向导及其数据校验，不改变正式随机事件的身份存储结构、审核方式或运行逻辑。保存到投稿和正式场景中的身份仍使用现有 `role + capacity` 结构，其中 `capacity` 固定为 `1`。

## 新投稿流程

1. 玩家填写场景名称、报名公告和事件参加人数。
2. 机器人提示玩家发送第一个身份名称，并显示已填写数量、总人数和剩余数量。
3. 每收到一个合法且不重复的身份名称，立即以 `capacity=1` 保存。
4. 身份数量少于参加人数时，继续提示发送下一个身份名称。
5. 身份数量等于参加人数时，直接进入事件名称步骤，不再出现身份人数确认。

身份名称仍限制为 1–32 字，同一投稿内不得重复。身份数量必须严格等于事件参加人数。身份数量上限等于本次事件参加人数，而事件参加人数继续受后台 `submission_max_participants` 配置限制；因此默认最高支持 99 个单席身份，不再受原有 20 种身份限制。

## 现有草稿兼容

已经停在旧 `role_capacity` 步骤的草稿不得作废或丢失内容。向导在恢复或处理下一条消息前执行一次兼容归一化：

- 读取 `_working_role`，以 `capacity=1` 保存该身份；
- 清理旧步骤使用的临时字段；
- 若身份数量已达到参加人数，进入 `event_name`；否则进入 `role_name`；
- 玩家仅发送 `/投稿 随机事件` 恢复草稿时，归一化后返回新的当前步骤提示；
- 玩家直接发送普通文本时，先完成归一化，再将这条文本作为归一化后步骤的输入处理，不把身份名称误当作人数，也不丢弃消息；
- 兼容逻辑只对仍处于 `role_capacity` 的草稿执行，完成归一化后不会重复添加身份。

若旧草稿数据异常，例如缺少 `_working_role`、身份已满或待保存身份与已有身份重复，则不静默制造重复数据：清理无效临时字段并回到根据当前身份数量计算出的合法步骤。

## 编辑、删除与返回

- `/修改身份 编号`：移除目标身份并进入身份名称步骤；玩家发送新名称后立即以 `capacity=1` 保存到原位置。身份修改会继续沿用现有规则，清空依赖旧身份变量的事件模板，避免留下无效引用。
- `/删除身份 编号 [编号...]`：删除指定身份并重新计算缺少数量，向导返回身份名称步骤补齐。
- `/上一步`：
  - 第一个身份尚未填写时，返回参加人数步骤；
  - 已填写部分身份时，撤回最后一个身份并提示重新填写身份名称；
  - 身份刚好填满并进入事件名称步骤后，返回时撤回最后一个身份并重新询问名称；
  - 不再返回已经移除的身份人数步骤。

## 模板与管理端

玩家侧不再使用 `/投稿` 的 `prompt_role_capacity` 模板。`prompt_role_name` 继续显示已填写、总人数和剩余数量。旧模板记录可以保留以兼容已有数据库配置，但新流程不得再渲染它。

管理端审核仍显示每个身份的席位数，所有玩家投稿身份均显示为 1。管理员审核阶段现有的场景编辑能力保持不变，本次不限制管理员将正式场景调整为多席身份。

## 校验与测试

实现必须覆盖：

1. 新投稿只输入身份名称即可完成全部身份；
2. 不再返回身份人数提示；
3. 每个保存身份的 `capacity` 均为 1；
4. 身份数量达到参加人数后自动进入事件名称；
5. 重复或非法身份名称不推进步骤；
6. 超过 20 人且不超过后台上限的单席身份可通过完整投稿校验；
7. `/修改身份`、`/删除身份` 和 `/上一步` 不进入旧步骤；
8. 停在旧 `role_capacity` 的草稿恢复时自动补 1；
9. 旧草稿收到普通文本时同时完成兼容并消费该文本，不丢消息；
10. 兼容处理重复执行不会重复添加身份；
11. 后台审核和正式随机事件场景仍接受并正确保存单席身份列表。

## 不在本次范围

- 不改变玩家投稿之外由管理员直接创建随机事件的多席身份能力；
- 不修改目标轮数、事件奖励或投稿奖励；
- 不改变投稿审核、通知、摸鱼币奖励或游戏门禁；
- 不对已经提交审核或已经生成的正式场景批量改写身份配置。
