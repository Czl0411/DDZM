# 随机事件结束前打赏环节设计

## 目标

为随机事件增加一个持久化的结束阶段。所有参与者退出剧情后，事件不再立即结束，而是进入默认 120 秒的公开打赏环节。所有已入职员工可以使用真实摸鱼币打赏本场参与者；倒计时结束或管理员强制结束后，系统公布汇总并正式释放随机事件占用。

本功能同时将员工展示名称改为全局唯一，使 `/打赏 员工名称 金额` 能够唯一、稳定地定位收款人。

## 已确认的产品规则

### 随机事件状态

随机事件状态流转为：

```text
signup -> in_progress -> tipping -> ended
```

- 参与者继续通过普通群聊累计随机事件轮数。
- 参与者仍需发送 `/退出` 离开剧情阶段。
- 达到目标轮数后退出，立即领取原有基础事件奖励。
- 未达到目标轮数而提前退出，基础奖励为 0，但仍属于本场参与者，之后可以被打赏。
- 最后一名仍在场的参与者退出时，不再立即结束事件，而是进入 `tipping`。
- `tipping` 写入开始时间和截止时间。时长来自随机事件设置，默认 120 秒。
- 截止时间在进入阶段时一次性计算；管理员之后修改默认时长不会改变已经开始的打赏阶段。
- 倒计时期间不再累计随机事件轮数，普通群聊恢复，也可继续进入正常的 AI 群聊记忆观察流程。
- 随机事件在 `tipping` 期间继续占用全局玩法槽位；不能开启其他游戏或新的随机事件。
- 倒计时到期后仅结算一次，并将状态改为 `ended`。
- Core、Browser Worker 或服务器重启不会重置倒计时；系统按数据库中的截止时间继续。
- 无人打赏时仍会正常结束，并公布“本场无人打赏”。

### 打赏资格与指令

指令格式固定为：

```text
/打赏 员工名称 金额
```

- 所有已入职员工都可以打赏，包括本场参与者和围观者。
- 收款人必须是本场随机事件的参与者，包括提前退出且没有获得基础奖励的参与者。
- 禁止给自己打赏。
- 金额必须是正整数。
- 余额必须足够，不允许透支。
- 同一员工可以在一个打赏阶段内多次打赏同一人或不同参与者。
- 打赏阶段结束、名称不存在、目标未参与、自赏、金额无效或余额不足时均不产生资金变化。
- 截止时间是半开边界：处理时间达到截止时间的打赏视为已结束。

### 真实摸鱼币流转

- 每次成功打赏都即时从打赏者余额扣除，并即时增加收款者余额。
- 不收手续费，系统不补贴也不回收金额。
- 同一数据库事务内完成事件校验、余额校验、付款、收款、双方流水和打赏明细写入。
- 付款流水来源为“随机事件打赏支出”，收款流水来源为“随机事件打赏收入”。
- 入站消息已具备平台消息 ID 幂等保护；打赏明细同时关联唯一入站消息，确保网络重试不会重复扣款。
- 余额与打赏记录是事实来源；回复发送失败只重试消息，不重复执行转账。

## 员工名称全局唯一

### 新规则

- 员工名称去除首尾空格后必须全局唯一。
- 名称按当前展示字符精确比较，`G` 与 `g` 视为不同名称。
- `/入职`、`/修改名称` 及其他写入员工名称的入口都必须先校验，并由数据库唯一约束兜底。
- 名称冲突统一回复：`名称已被占用。`
- 打赏阶段禁止 `/修改名称`，避免已公布的参与者名单失效。

### 历史重名迁移

- 迁移只修改存在冲突的历史名称；多数员工的名称保持不变。
- 同一重复名称组内的所有员工改为 `原名称#工号`，例如 `小明#0015`。
- 工号使用现有永久员工工号，因此同组生成结果天然不同。
- 如果生成结果又与另一个历史展示名称相撞，则继续给发生冲突的历史名称追加其员工工号，直至全表唯一。
- 完成数据整理后，再建立数据库唯一约束，避免迁移过程中留下歧义。

## 数据模型

### 随机事件设置

`random_event_settings` 增加：

- `tipping_duration_seconds`：正整数，默认 `120`，后台允许范围 `10–3600`。

### 随机事件记录

`random_events` 增加：

- `tipping_started_at`：进入打赏阶段的北京时间，可空。
- `tipping_deadline`：打赏截止时间，可空。

现有“全局仅一个活动随机事件”索引的活动状态范围由 `signup`、`in_progress` 扩展为 `signup`、`in_progress`、`tipping`。

### 打赏明细

新增 `random_event_tips`：

- `id`
- `event_id`
- `sender_user_id`
- `recipient_user_id`
- `amount`
- `inbound_message_id`，唯一
- `created_at`

按 `event_id` 建立查询索引，用于阶段汇总与后台详情。记录引用用户 ID，不依赖之后可能变化的显示名称；群消息和后台展示时读取当前已锁定的唯一名称。

## 核心事务与并发

### 进入打赏阶段

`/退出` 在现有事务内锁定活动事件和参与者：

1. 按原规则决定是否发基础奖励并记录 AI 活动事实。
2. 标记当前参与者退出。
3. 如果仍有参与者在场，返回原退出结果。
4. 如果这是最后一名参与者，将事件改为 `tipping`，写入开始时间与截止时间，并入队“进入打赏阶段”消息。

同一事件只有第一次“最后一人退出”可以完成状态转换。

### 执行打赏

打赏事务按以下顺序执行：

1. 锁定当前活动随机事件，要求状态为 `tipping` 且当前时间早于截止时间。
2. 查找打赏者及名称唯一的收款者。
3. 验证双方不是同一人，且收款者在本场参与者表中。
4. 按用户 ID 固定顺序锁定付款人与收款人，避免反向打赏形成死锁。
5. 验证付款余额。
6. 写入打赏明细和双方余额流水，同时更新双方余额。
7. 入队单次打赏成功回复。

事件结束、管理员强制结束和打赏使用同一事件行锁。状态转换先成功的一方生效，晚到打赏不会扣款。

### 自动结束

现有随机事件定时任务增加 `tipping` 检查：

1. 锁定已到截止时间的打赏事件。
2. 从持久化打赏明细生成汇总。
3. 将事件和日程状态改为 `ended`，写入结束时间。
4. 入队最终汇总消息。

状态更新与汇总消息入队在同一事务内，重复任务只会看到已经结束的状态，不会重复结算。

### 强制结束

- 董事会成员和后台可以在 `signup`、`in_progress` 或 `tipping` 阶段强制结束随机事件。
- 在 `tipping` 阶段强制结束会立即停止继续打赏。
- 已成功转出的摸鱼币不退款。
- 系统生成截至强制结束时的打赏汇总，然后正式释放玩法占用。

## 命令门控与普通聊天

- `tipping` 期间普通非指令群聊不再作为随机事件剧情，不增加轮数，也不触发随机事件观察者格式限制。
- 普通群聊可按系统原规则进入 AI 记忆候选。
- `/打赏` 必须在 `tipping` 阶段开放。
- `/余额`、红包等既有独立指令继续按原有独立指令规则工作。
- 新游戏、新随机事件和 `/修改名称` 继续被随机事件门控拒绝。
- `/当前游戏` 显示“随机事件打赏中”、场景名称和剩余秒数。

## 群消息与回复模板

### 进入打赏阶段

默认消息：

```text
【随机事件：{场景名称}】剧情阶段已结束，进入打赏环节（{打赏秒数} 秒）。
可打赏员工：
{参与者与基础奖励列表}
发送：/打赏 员工名称 金额
```

参与者列表展示每位参与者当前唯一名称和基础奖励；没有完成目标轮数者显示基础奖励 0。

### 单次成功

成功消息使用对原打赏指令的回复定位：

```text
{打赏者} 向 {收款人} 打赏了 {金额} 摸鱼币。
```

### 最终汇总

- 参与者按收到的打赏总额从高到低排列；同额时按员工工号升序，保证顺序稳定。
- 每位参与者下方按打赏发生时间列出打赏者与金额。
- 没有收到打赏的参与者仍显示 `0 摸鱼币`。
- 全场没有打赏时追加“本场无人打赏”。

默认结构：

```text
【随机事件打赏结束】
{参与者打赏汇总}

本场随机事件正式结束。
```

以下场景纳入现有回复模板管理：

- 进入打赏阶段
- 使用格式
- 打赏成功
- 尚未入职
- 不在打赏阶段或阶段已结束
- 金额无效
- 员工名称不存在
- 目标不是本场参与者
- 禁止给自己打赏
- 余额不足
- 自动结束汇总
- 强制结束汇总

## 后台管理

- “随机事件规则”增加“打赏时长（秒）”，默认 120，范围 10–3600。
- 今日随机事件和当前玩法状态展示 `打赏中`、截止时间、剩余秒数和已收打赏总额。
- 随机事件详情展示每笔打赏的打赏者、收款者、金额和时间。
- 后台强制结束按钮支持 `tipping`。
- 员工摸鱼币流动日志展示打赏支出和打赏收入。

## 帮助与 AI 玩法指引

- 命令定义新增 `/打赏 员工名称 金额`。
- `/帮助 随机事件` 增加打赏说明。
- AI 随机事件知识卡说明：打赏只在所有参与者退出后的限时阶段开放，真实转移摸鱼币，不能自赏。
- AI 只解释并引导玩家发送准确指令，不代替玩家执行打赏。

## 数据迁移与兼容

- 增加设置字段、随机事件截止字段、打赏明细表和相关索引。
- 更新活动随机事件唯一索引，使 `tipping` 也占用全局随机事件槽位。
- 在建立员工名称唯一约束前完成历史重名整理。
- 迁移时已有的 `signup`、`in_progress`、`ended` 等事件保持原状态；不会凭空进入打赏阶段。
- 迁移前已完成的随机事件不生成打赏记录。
- 默认回复模板和命令定义通过现有幂等初始化同步，不覆盖管理员已经自定义的其他模板。

## 测试与验收

### 随机事件状态

- 非最后一人退出保持 `in_progress`。
- 最后一人退出进入 `tipping`，不立即 `ended`。
- 完成者获得基础奖励，提前退出者基础奖励为 0，但两者都在打赏名单中。
- `tipping` 期间普通聊天不增加轮数，新玩法仍被阻止。
- 零打赏、正常打赏、重启恢复和到期任务均只结束一次。

### 打赏资金

- 成功打赏原子扣款与入账，金额守恒。
- 自赏、未入职、无效金额、名称不存在、非参与者、余额不足、阶段错误和超时均不写流水。
- 多次打赏可累积。
- 并发打赏不会透支；反向并发打赏不会死锁。
- 重复平台消息不会重复扣款。
- 自动结束或强制结束与打赏并发时，不出现结束后扣款。

### 名称唯一

- 历史重复名称迁移为带永久工号的唯一名称。
- 非重复历史名称保持不变。
- `/入职` 和 `/修改名称` 的同名请求返回“名称已被占用”。
- 并发写入同一名称时仅一个成功，数据库约束兜底。
- 大小写不同的名称按规则分别允许。

### 消息与管理

- 进入阶段、单次回复定位、最终排序与零打赏文案正确。
- 后台设置范围校验、状态、截止时间、金额汇总和明细正确。
- 董事会与后台强制结束保留已到账打赏并只发一次汇总。
- `/当前游戏`、帮助、命令库、AI 知识卡和员工资金流水覆盖新功能。

## 不在本次范围

- 打赏手续费、系统补贴、退款、撤回或匿名打赏。
- 每日打赏次数或金额上限；仅受实际余额限制。
- 给非参与者、部门或系统账户打赏。
- 打赏榜的长期统计与额外成就奖励。
