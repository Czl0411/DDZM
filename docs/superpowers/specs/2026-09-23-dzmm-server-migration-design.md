# DZMM 服务器迁移设计

## 目标

将 DZMM 从旧服务器 `43.134.78.52` 完整迁移到新服务器
`49.234.20.159`，保留 PostgreSQL 数据、浏览器登录状态、运行配置和
systemd 服务。切换后只允许新服务器运行 DZMM，旧服务器保留为停止状态的
回滚副本。

## 已确认约束

- 最终切换允许暂停机器人服务约 10–15 分钟。
- 新服务器管理后台监听 `0.0.0.0:18080`。
- 核心 API 继续监听 `127.0.0.1:18120`。
- 浏览器 CDP 继续监听 `127.0.0.1:19222`。
- 不迁移旧服务器上的 OpenClaw 等非 DZMM 服务。
- AI 记忆功能保持关闭：数据库设置为关闭，AI 记忆 worker 保持 disabled。
- 旧服务器及其数据库在迁移完成后不删除，用于回滚。
- 迁移过程不得在日志、终端输出或仓库中泄露环境密钥和数据库密码。

## 当前状态

旧服务器运行 Ubuntu 24.04、PostgreSQL 16.14，DZMM 数据库约 327 MB，
浏览器状态目录约 41 MB，Alembic 版本为 `20260919_82`。新服务器运行
Ubuntu 24.04，约有 26 GB 可用磁盘和 2.8 GB 可用内存，当前未安装 DZMM
服务和 PostgreSQL。

## 迁移方案

采用“预部署 + 最终冷切换”。旧服运行期间完成新服基础环境、PostgreSQL、
应用代码、systemd 单元和配置准备，但不启动会读取消息或写入业务数据的服务。
先使用一致性数据库备份做恢复演练，证明新服数据库和应用能够启动，然后清空
演练数据，等待正式切换。

正式切换时停止旧服全部 DZMM 服务，使数据库进入无业务写入状态。随后创建最终
PostgreSQL 自定义格式备份，并在浏览器 worker 停止后同步浏览器状态目录。新服
恢复最终备份、校验 Alembic 版本和关键记录数量，再按 core、admin、browser、
普通 AI worker 的顺序启动服务。AI 记忆 worker 不启动。

新旧服务器之间的数据通过受控 SSH 通道传输；密钥配置文件保持 root 所有、
权限 `0600`，浏览器状态保持 dzmm 用户所有。Python 虚拟环境不复制，在新服
依据项目依赖重新创建。

## 数据一致性

运行中的 `pg_dump` 能提供一致性快照，但不能包含备份完成后产生的新消息和交易，
因此预演备份不能作为最终数据。最终备份必须在旧服 DZMM 服务全部停止后生成。
恢复期间新服业务服务保持停止，避免迁移未完成时写入数据库。

正式切换前记录旧服以下基线，并在新服恢复后对比：

- 数据库大小和 Alembic 版本；
- 用户、入站消息、出站消息、余额流水、游戏与随机事件等核心表行数；
- 待处理出站消息和 worker 任务数量；
- AI 记忆设置关闭状态；
- 浏览器状态目录大小和所有权。

## 服务与端口

新服安装并启用以下服务：

- `dzmm-core.service`：`127.0.0.1:18120`；
- `dzmm-admin-web.service`：`0.0.0.0:18080`；
- `dzmm-browser-worker.service`：负责平台登录和消息收发；
- `dzmm-ai-worker.service`：普通 AI 任务；
- `dzmm-ai-memory-worker.service`：安装但保持 disabled/inactive。

新服启动前确认目标端口未被占用。旧服 DZMM 服务停止后，非 DZMM 服务保持原状。

## 验证标准

只有同时满足以下条件才视为迁移成功：

1. 新服 Alembic 版本为 `20260919_82`，数据库核心表计数与切换基线一致。
2. Core 健康检查报告数据库可用，worker 心跳正常。
3. Core、Admin、Browser、普通 AI worker 均为 active 且无重启循环。
4. AI 记忆设置为关闭，AI 记忆 worker 为 disabled/inactive。
5. 管理后台通过新服务器 `18080` 端口可访问。
6. 浏览器状态被正常加载，不要求用户重新登录；若平台主动使会话失效，则停止切换
   并由用户完成登录后再继续。
7. 实际执行一组低风险冒烟检查：读取当前状态、接收一条测试指令并成功回复。
8. 新服观察至少五分钟，无持续错误、无消息积压增长、CPU 和内存稳定。

## 回滚

在新服验证完成前，不修改或删除旧服数据库和浏览器状态。如果新服数据库恢复、
登录状态、消息收发或健康检查任一失败：

1. 立即停止新服全部 DZMM 服务；
2. 确认新服不再产生业务写入；
3. 重新启动旧服 Core、Admin、Browser 和普通 AI worker；
4. 保持旧服 AI 记忆 worker 关闭；
5. 验证旧服健康和消息收发后结束回滚。

一旦新服开始接收真实业务消息，禁止在不处理新服新增数据的情况下直接把旧服重新
上线，以免形成两份分叉数据。成功观察期结束后，旧服继续保持停止，等待用户另行
决定何时销毁。
