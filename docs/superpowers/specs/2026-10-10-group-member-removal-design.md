# 群聊成员移除指令设计

> 状态：交互设计已确认，功能已实施。

## 目标与范围

允许后台按群指定已入职员工使用 `/ban`，让其在群里回复一位**未入职**成员的消息，填写原因并经过二次确认后，由“总监事”账号将该成员移出**当前群**。这是移出群聊，不是平台封号、禁止重新入群、删除消息或扣币。

成功标准：未经授权、目标已入职、无有效回复、未经本人确认、跨群确认或超时确认都不会触发平台移人；只有平台操作确认成功，Bot 才称“已移出”。

## 后台授权

- 在现有“群聊管理”的编辑页为每个群增加“可使用 `/ban` 的员工”多选配置，默认无人获权。候选人仅来自已入职员工。
- 列表以公司名称显示，辅以平台昵称和工号区分同名；平台 UID 仅作为存储与请求标识，不要求管理员记忆 UID。
- 每群授权独立。保存时验证所选平台 UID 对应现存员工；改名后界面自动显示新名称。撤销授权应使该员工未确认的请求失效。
- 不根据公司职位、平台群管理身份或其他群的授权自动赋权。后台管理员沿用现有群聊配置页的权限控制。

## 群内操作

1. 授权员工在受监听的群中回复目标的一条消息，发送 `/ban 原因`。原因不能为空；不接受私聊、无回复、回复自己或缺少有效作者 UID 的引用。
2. Bot 从回复引用读取原作者平台 UID 和原消息 ID，不按昵称猜测。若目标 UID 已存在于公司员工表，拒绝；Bot 自身和长消息 Bot 也不作为目标。
3. Bot 在同群提示：`是否移除 UID <目标UID>？`，并显示被回复的文字摘要（图片显示“[图片]”）、原因和“发起人请在 60 秒内发送 /是”。此时尚不移人。
4. 仅原发起人在同一个群发送**独立的、精确的** `/是` 才确认。按“发起人 + 群”最多保留一条待确认操作；再次 `/ban` 以新请求替换旧请求。其他人、其他群、过期后的 `/是` 不生效，重复确认也不得产生第二次移人任务。
5. 确认时再次核对后台授权和目标未入职。通过后只提示“正在移除”，待平台返回后再报告最终结果。

`/ban` 和 `/是` 是群管理指令；随机事件、小游戏或公演进行中仍可用，不计入这些玩法的发言或轮次。不会为目标创建公司员工记录。

## 执行与数据

- 使用现有 Core/Worker 边界：Core 存储按群授权、带 60 秒有效期的待确认操作和审计结果；确认后以稳定的操作 ID 投递到现有 Worker 命令队列。Bot 消息仍走现有出站队列。
- Worker 持有平台登录态，执行前再次向 Core 检查操作状态、授权和目标未入职，然后调用平台的 `groupChat.removeMember` mutation，参数为 `{chatroomId, memberId}`。该调用已在 2026-10-10 平台前端资源中核对；不将 `/ban` 的原因当作平台参数。
- Worker 把平台成功或失败结果回写 Core；Core 根据确认消息在原群发送一次最终反馈，并记录群、发起人、目标 UID、原消息 ID、原因、时间和结果。
- 平台拒绝、目标已离群、授权被撤销或目标已入职时不报移出成功。请求超时或结果不明时标记失败/待核查，不无限重试移人；重新操作必须从新的 `/ban` 开始。
- 操作记录和状态转换应防止同一确认重复入队。Worker 重领任务时先检查记录状态，避免已经完成的操作再次调用平台。
- 移人执行中，目标暂不能入职，以免在检查后、平台移人前成为员工；平台结果不明时继续保留该限制，须由管理员核查并处理后才能恢复入职。

## 验证

- Core 测试：每群授权与名称显示、未授权拒绝、已入职目标受保护、回复目标 UID 提取、无原因/无回复/回复自己、60 秒边界、跨人跨群确认、后发请求替换先发请求、授权撤销及目标在确认前入职、重复 `/是`。
- 路由测试：随机事件、游戏、公演进行中 `/ban` 与 `/是` 可到达管理流程且不被记为玩法发言。
- Worker 适配测试：`groupChat.removeMember` 请求参数、成功、平台拒绝、超时与重复领取；最终群消息只能在确认结果后发出。
- 后台测试：群聊授权名单保存/重开仍保留，以名称、平台昵称、工号展示；不同群互不影响。
- 不以真实成员做破坏性验证。部署前运行相关自动化测试；真实平台权限由已具备群管理身份的“总监事”账号执行。

## 不做

本期不做永久封禁、自动退群冷却、按职位授权、批量移人、跨群移人、后台直接移人、未入职人员使用 `/ban`、移除已入职员工或删除被引用消息。
