# DZMM 群聊象棋 H5 设计

## 目标与范围

群成员在已监听群聊发送 `/象棋` 后，Bot 在原群发布该盘的 H5 链接和一次性四位数字入座码。发起者占第一个棋手位，另一位已入职的 DZMM 用户先输入正确入座码先得；其他已入职用户可以观战。双方在 H5 内完成标准中国象棋对局，断线后可回到原盘，Bot 只在终局向原群通报结果。

首版不涉及摸鱼币、AI 棋手、自动匹配、段位或排行榜。游戏内有本局文字聊天，棋手和观众均可发言；聊天不进入长期史册。该游戏可与现有群聊小游戏并行；同一群可同时开多盘，同一用户也可同时参加多盘，每盘独立计时。

## 已确认玩法

### 发起、入座、观战

- `/象棋` 只在 Bot 已监听的群聊触发；发起者必须已经通过 `/入职`。当前 `UserRecord.platform_id` 在全局唯一，因此“已入职”不要求在发起群再次注册。
- 每次成功发起生成独立棋局 ID、H5 入口链接和四位数字入座码。Bot 在该群发布链接和入座码，并说明“另一位已入职用户先输入先得，其他人可观战”。创建者占首位，但红黑双方直到第二位加入后才随机决定。
- 第二个棋手必须与发起者不同。两个不同账号并发提交正确入座码时，只能有一个成功；成功后入座码立即失效。
- 入座码自创建起 10 分钟有效；逾期未有人入座则棋局取消，并由 Bot 在发起群通知。已取消的链接显示原因，不得再入座或开局。
- 任何已入职用户均可凭棋局链接观战，无须入座码；即使链接被转发到别的群，已入职用户仍可抢第二位或观战，但终局消息仍回原发起群。
- 未登录或未入职的访问者不能进入棋局或聊天，页面引导先登录／入职。入座码不是身份凭据；每个请求仍须验证平台登录身份。
- 入座成功后立即随机分配红黑，红方先行。棋手可在 H5 中看到自己执哪方；观众看到双方名称、棋盘和时钟。

### 行棋与计时

- 采用标准中国象棋棋盘和走法，按《中国象棋竞赛规则（2020 版）》处理将死、困毙、认输、和棋及重复局面。不能把“三次重复”简单判成自动和棋；长将、长捉等须由服务端规则裁决。首版不添加自行改造的棋规。
- 每方总用时 15 分钟，每步最长 60 秒，无加秒。轮到一方时，该方总时间和本步时间同时流逝；任一时间先归零即判该方超时负。开局前不走钟。
- 服务端是棋盘、合法着、回合、时钟和结果的唯一权威。前端只能提交起点、终点和当前棋局版本；服务端校验身份、轮次、棋规、时钟与版本后才落子。重复或过期请求不能落第二次子。
- 断线不暂停时钟；玩家用同一 DZMM 账号重开该盘链接即可恢复身份、棋盘、着法和剩余时间，不再输入入座码。不同棋局的计时互不影响。
- 棋手可提出悔棋或和棋，均须对手同意才生效；待决请求不暂停时钟。悔棋只撤销最近一步，双方已消耗的时间不退还，回到撤销前的行棋方。认输由本人确认后立即终局。观众不能执行上述操作。
- 终局后棋盘和着法可查看，不能再落子或聊天；Bot 对发起群发送一次结果，不逐步广播行棋。

### 本局聊天

- 两名棋手和已入职观众都能发送纯文字聊天；消息只显示在当前棋局的聊天区，不转发到群聊。
- 重连可查看该局进行中已保存的聊天。终局后不提供长期聊天史册或对外查询；赛后保留棋谱和结果不包含聊天正文。
- 聊天消息携带经服务端确认的发送者身份和时间；客户端提交的昵称或角色不可信。文本按现有产品内容规范处理，并限制长度与发送频率，避免刷屏。

## 技术方案与边界

### 方案选择

比较过三种方式：仅用 `dzmm.rt` 房间、仅用 Gamefy 服务端函数加共享 KV、Gamefy H5 加现有 DDZM 后端。前两者分别受宿主离开即结束房间，以及共享 KV 缺少更新事务／CAS 的限制，不能可靠支持断线重连、抢座和权威落子。选用第三种：Gamefy 承载棋盘界面和平台身份入口，现有 DDZM 后端承载棋局状态与实时服务。

### 组件与数据流

1. **Bot 指令入口**：沿用现有群聊消息接收和群组识别。校验监听群与发起者已入职，创建独立棋局。象棋不进入 `active_gameplay_summary` 的群级互斥集合，亦不占用通用 `/加入`、`/退出`、`/当前游戏`、`/结束游戏` 路由。指令 `/象棋` 本身没有继续游戏的群聊命令。
2. **链接**：在后台配置已发布的 Gamefy 游戏卡入口；Bot 生成携带该盘棋局 ID 的入口链接，所传 `gp` 仅是定位参数，不是身份或授权。H5 启动时读取并校验 `dzmm.getLaunchParams()`，然后只向本后端请求该棋局。平台会在读取后清除启动参数，客户端须记住正在访问的棋局 ID 以便本页刷新恢复。发布前必须在真实 DZMM 玩家会话验证 Bot 发出的链接能打开指定棋局；Workbench 预览不支持 `dzmm.share()`，不能代替这一验收。
3. **身份**：H5 从 `dzmm.user.info()` 取得短时效 token，请求 DDZM 后端时以 Bearer token 提交。后端通过平台 JWKS 验证 RS256 签名、`iss=dzmm-gamefy`、当前游戏的 `aud`、过期时间，再以 `sub` 匹配本地 `UserRecord.platform_id`。不能把客户端传来的用户 ID、昵称或 `gp` 当作身份。token 到期时 H5 重新取得 token，再恢复连接。
4. **棋局服务**：持久化棋局、棋手、原群、状态、棋盘／着法、双方时钟、当前步截止时间、版本、终局结果。抢第二位、行棋、悔棋／和棋确认和终局必须是数据库原子状态转移，使用行锁或等价并发控制；不能先读再无条件写。每次状态转移以服务端时间结算时钟。
5. **实时通道**：H5 与现有后端建立棋局订阅，服务端推送盘面、计时基准、提议状态、聊天和终局。客户端断线重连后先拉权威快照再订阅增量；订阅断开不会改变棋局状态。推送只是展示，所有动作以持久化事务结果为准。网络延迟下的计时显示按服务端时间基准估算，终局仍由服务端判定。
6. **定时推进**：后端定时检查待入座过期、轮到棋手的步时／总时到期，执行一次性终局。若服务重启，依据持久化截止时间恢复，不从重启时重新计时。Bot 通告走现有出站消息机制，以棋局 ID 和事件类型去重，重试不能重复发终局消息。

### 状态与主要操作

棋局状态为 `waiting`（等第二人）、`playing`、`finished`、`cancelled`。`waiting` 仅可成功抢座或到期取消；`playing` 可行棋、协商、认输或超时；`finished` 和 `cancelled` 是终态。每盘独立状态，没有群级活动棋局记录或玩家级唯一活动棋局约束。

玩家进入时默认是观众；创建者经身份识别自动成为棋手，第二位成功抢座者成为另一棋手。入座请求仅在 `waiting` 且验证码正确且未过期时生效。聊天按棋局 ID 隔离，终局立即关闭写入；聊天保留期限以实现进行中重连为限，不混入棋谱或长期玩家档案。

## 错误提示与安全

- 无效／过期／已使用入座码、自己抢第二位、未入职、棋局已结束，都返回明确且不泄露其他棋局状态的提示。
- 越权走棋、非本人提议确认、观众操作、非法着、非当前回合、旧版本提交一律不改变棋局；客户端刷新权威快照。
- Bot 创建棋局成功但群消息发送失败时，不留下无法发现的可抢座棋局；需标记取消或由可靠出站任务补发，并保证最终一致。
- 四位码公开在原群，本质是先到先得的入座门票，不承诺隐私或防转发。服务端仍校验平台账号和入职记录。
- H5 只请求本项目后端，不把平台 token 写入 KV、聊天内容、URL 或日志。后端对聊天内容做长度和速率限制。

## 验证与验收

- 棋规测试覆盖每类棋子走法、蹩马腿／塞象眼、将帅照面、将军应对、将死、困毙、长将／长捉和典型重复局面；结果与已确认的 2020 规则一致。
- 计时测试使用可控时钟验证 15 分钟总时、60 秒步时、无加秒、断线继续、服务重启恢复及临界时刻落子／超时的唯一结果。
- 并发测试同时提交同一入座码、同一版本的两步棋和相反的终局操作，证明每次只成功一次。
- 身份测试覆盖缺失／伪造／过期 token、错误 `aud`、未入职账号、观众越权及已入职跨群访问。
- 端到端测试在真实发布的 Gamefy 页面中验证群聊指令、Bot 链接、抢座、观战、聊天、重连、终局通告，以及同群多盘、同一用户多盘、与现有小游戏并行。
- 验收标准：棋手与观众看到同一权威局面；抢座不重位；重连不重置时钟；终局只判一次、通报一次；对局期间不阻塞现有群聊游戏和指令。
