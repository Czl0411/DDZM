# 群聊斗地主 H5 首版设计

状态：用户已确认，本地首版已实现；真实验证结果、暂缓问题和上线闸门见 `docs/doudizhu-deployment.md`，尚未发布。

## 1. 目标与边界

让已入职群友从小游戏群发起三人斗地主，在 Gamefy 内完成入座、准备、叫分、出牌、聊天和观战；不用学习新的扑克玩法。界面采用经典绿绒牌桌和常见操作位置，自绘牌面，不复制其他产品品牌、人物或素材。

用户已授权按主流规则和 UI 决定细节。首版采用经典三人叫分制，不做癞子、抢地主、比赛场、充值、自动匹配或强 AI。无摸鱼币扣发；倍数仅作本局战况展示，不创建币流水或账户积分。

小游戏群：`4fc4a2fd-465a-4436-9884-dbb5e60c6af2`。斗地主使用独立 Gamefy 游戏卡，不覆盖象棋卡 3761638。新卡创建与平台审核安排在后续实施阶段，不能假定已有可用卡 ID。

参考：

- [JJ 官方斗地主介绍](https://www.jj.cn/ddz/)：54 张牌、三人、17 张手牌与 3 张底牌、1/2/3 叫分及全不叫重发。
- [JJ 帮助中心牌型规则](https://www.jj.cn/news/320/20110920103700018196.shtml)：牌型和比较方式。不同产品及历史规则存在差异，以下明确本项目采用的变体边界，不宣称所有平台一致。
- 本仓库 Gamefy 象棋实现与用户提供的 Gamefy 开发文档：SDK、沙箱、身份接口和服务端能力约束。

## 2. 已定玩法

### 开局与席位

1. 已入职用户在小游戏群发送 `/斗地主`，创建独立房间并占首席。
2. Bot 分别发送游戏分享卡和文字消息，文字含短房间编号、四位数字入座码、10 分钟有效期及玩法入口说明。
3. 另两名不同的已入职用户以 SDK 提供的 UID 查询员工身份后输入入座码，按服务端事务成功顺序入座。四位码是公开门票，不是登录凭据；第一个人加入后仍可供第二个人使用，满员即失效。
4. 满三人后由所有玩家点击准备。第三个人准备成功时只发牌一次；首发前可取消准备、离开席位，房主离开则取消房间。
5. 自创建起 10 分钟内未完成三人准备则取消，不让空房无限等待。只有群内文字消息发送成功的房间可以抢座。
6. “已入职”沿用现有全局员工 UID 注册数据，不要求在小游戏群重复入职。公开门票不保证只能原群用户使用，转发后其他已入职用户也可能加入。
7. 多个房间可以并行，也不与象棋、群聊游戏争用互斥锁。不占用通用 `/加入`、`/退出`、`/结束游戏` 等指令。

### 发牌与叫分

- 服务端使用安全随机源洗一副 54 张牌，牌有唯一 ID；发 17/17/17 张，余 3 张底牌。确定地主前不向任何客户端下发底牌。
- 每副牌随机首叫席位，按固定席位循环叫分。每人最多叫一次，可不叫或叫高于当前最高分的 1/2/3 分；叫到 3 分立即结束叫分，否则一圈后最高分者为地主。
- 地主取得并公开 3 张底牌，持 20 张，先出牌。另两人同为农民。
- 全不叫重新洗牌发牌。为避免无人操作导致无限重发，连续三副牌全不叫后取消本房间，并提示重新开局；这是本项目的空转保护，不是统一竞赛规则。
- 没有明牌、加倍／超级加倍按钮。叫分是基础倍数，炸弹、王炸、春天按下面规则展示。

### 牌型与比较

- 大小顺序：3 < 4 < … < 10 < J < Q < K < A < 2 < 小王 < 大王，花色不比较。
- 支持：单张、对子、三张、三带一、三带一对、顺子、连对、飞机、飞机带单、飞机带对、四带二单、四带两对、炸弹、王炸。
- 顺子至少 5 张；连对至少 3 对；飞机主体至少连续 2 组三张。所有连续主体只允许 3～A，不包含 2 或王。
- 三带一的单牌、三带对的对子必须与三张主体不同点数。
- 飞机带单：每组三张带一张，翅膀可含对子作为两张单牌，但不能含主体点数、不能同时带大小王、不能把四张同点数当作单翅膀。
- 飞机带对：每组三张带一对，对子的点数必须互异且与主体不同；四张同点数不能拆成两对翅膀。
- 四带二单可以带一对作为两张单牌，但不能带大小王组合；四带两对要求两对点数不同。四带二不是炸弹。
- 普通牌必须与被压的牌型、总张数和主体长度相同，只比较主体点数。炸弹压普通牌，大炸弹压小炸弹；王炸最大。
- 一组牌如能解释为不同飞机主体，枚举合法解释，使用能压过当前牌的最小合法主体；主动领出时采用最大的合法主体。界面显示服务端确认的牌型，不让前后端自行选择不同解释。
- 连续两家不出后清空本轮待压牌，由最后出牌者重新领出。领出时不能点“不出”；能够压牌时仍允许主动不出。
- 任意一人出完牌即结束：地主先出完为地主胜；任意农民先出完为两名农民共同胜。
- 每个炸弹或王炸让展示倍数乘 2。地主获胜且两名农民均未出过牌为春天；农民获胜且地主仅出过一次牌为反春，额外乘 2。两者不同时成立。

### 计时、托管与退出

- 叫分每人 15 秒，出牌每步 25 秒，无象棋式总用时。这些是本项目默认值。
- 超时进入托管：叫分选择不叫；跟牌默认不出；领出选择最小单张。托管只保证合法和能推进，不宣称有高手策略。
- 托管决定仍只依据该玩家手牌及公开牌局，不能读取对手手牌来选择动作。
- 玩家可点“取消托管”，只对下次未处理的行动生效；操作和定时器并发只执行一个合法动作。
- 断线不暂停计时、不释放席位。首发后离开页面仍占原席位，不能让别人替换看过手牌的人；返回后恢复手牌、身份、回合和剩余时间。
- 对局中不提供悔牌、求和或个人直接结束整局，避免泄露信息后撤销。主动离开提示将进入托管，可重新连接。
- 终局后显示地主、两名农民姓名、胜负、春天状态和展示倍数；Bot 向原群发送一次全中文结算，无英文代码或长 UUID。
- “再来一局”回到同一房间的准备阶段，三人重新准备后建立新局次、重新洗牌；历史结果独立保留，不能把上一局的迟到请求应用到新局。

## 3. 界面与交互

- 绿绒桌面、暖金装饰、白色实体牌面；重点是牌点和按钮清楚，不堆人物动画、广告或消费入口。
- 自己手牌固定在下方，对手在左上和右上：显示姓名、地主／农民标记、剩余张数、在线／托管状态和当前回合倒计时。
- 顶部显示房间短编号、已公开底牌与本局倍数。桌面中央保留三家最近出牌／不出的信息，归新轮时明确刷新。
- 点击选牌上浮，再点取消；手牌按点数降序排列。支持连续滑选，手指移过同张牌不能反复切换。窄屏最多分两排，20 张手牌不能被裁切或必须横向滚动才能看全。
- “不出／提示／出牌”在手牌上方。提示循环选择合法可压牌组合，不自动提交；没有可压牌时明确提示。首家出牌隐藏或禁用“不出”并解释原因。
- 对手身份、手牌计数和轮次用文字及视觉标记共同表达，不只依赖颜色。未轮到本人不能误出牌，旧版本返回明确提示并恢复服务器快照。
- 顺子、连对、飞机、炸弹、王炸、春天显示短文字动效；剩 2 张／1 张明确提醒。首版不加音效和语音素材。
- 手机竖屏为主要验收，横屏和桌面横向铺开。聊天折叠面板不得挡住出牌按钮；不要求设备强制横屏或浏览器全屏权限。
- 所有按钮通过点击事件请求，不依赖 HTML 表单提交，兼容已确认不含 `allow-forms` 的 Gamefy 沙箱。

## 4. 观战与聊天

- 所提供 UID 对应已入职员工的用户可观战，不占席位。观众视图只显示已出牌、已公开底牌、手牌数量和公共状态，不下发任一玩家剩余手牌。
- 对局结束后也不额外公开未出完的手牌；首版不提供全手牌回放。
- 玩家与观众可以在房间内公开聊天，等待准备和对局阶段均可用。没有农民专属私聊，也不把聊天自动转发到群。
- 每条 1～300 字，单人至少间隔 2 秒；展示服务端员工名称，纯文本渲染，不能插入 HTML。
- 首版聊天只服务本房间交流，终局后停止写入，保留当前结果页可见记录；不加入长期史册。新局次聊天另起，不混入前局。
- 公共出牌记录、倍数和结果按局次保存，方便重连及去重；记录中不得携带隐藏手牌。

## 5. 身份和手牌保密

### 按用户选择仅信任 UID

用户明确选择与当前象棋相同的 UID 信任模式。首版不要求平台 JWT、不签发登录令牌、不增加私聊验证码或 `/斗地主验证` 指令。

1. H5 从平台 SDK 读取 UID，请求时提交该 UID；后端查全局员工表，拒绝缺失、格式无效、不存在或未入职的 UID。
2. 玩家姓名由员工表读取，席位与操作权限依据请求提供的 UID 判断；不能由客户端另传席位或姓名来覆盖。
3. HTTP 和 SSE 按该 UID 构建视图：属于玩家席位时只附加该席位手牌，否则仅给观众公共信息。后端仍检查牌归属、轮次和合法行动。
4. 页面重开后重新读取 SDK UID，并通过最近房间编号恢复原席位；无需输入登录验证码。UID 读取失败时显示读取失败并允许重试，不伪称登录失效、不回退到其他玩家 UID。
5. 四位入座码仅控制空席位加入，不验证本人身份。平台 KV 仅用于最近房间编号，不保存手牌。

风险边界：SDK 读取的 UID 一旦通过客户端请求传入，后端无法证明请求者就是本人。伪造已入职玩家 UID 可以冒充其身份、读取其手牌或代为出牌，员工登记检查和按 UID 分发视图均不能防止这种攻击。此方案只提供正常客户端使用下的手牌隔离，不承诺防冒充；首版仍不涉及摸鱼币或其他资产操作。

## 6. 技术结构与方案取舍

### 选择现有后端权威牌局

可选方向：平台实时房间托管、Gamefy 服务端函数共享 KV、现有 DDZM 后端。前两种需要重新验证持久化、原子更新和宿主生命周期；平台函数目前又不能直接外联本后端，也没有文档确认的秘密签名能力，不把未验证能力作为前提。采用第三种。

- 新建独立 `doudizhu_rules`、`doudizhu_repository`、`doudizhu_api` 与 `gamefy/doudizhu`，不重构现有象棋或通用群游戏。
- 规则层只负责牌型、比较、合法行动、可出牌提示和胜负，无网络／数据库依赖。
- 数据层保存房间、席位、局次、私有手牌、底牌、状态、轮次、截止时间、版本、托管、公共行动记录、聊天与终局出站标记。
- 沿用 UID 信任模式的接入方式，不新增鉴权会话或验证码表，不改现有象棋身份逻辑。
- Bot 沿用现有入站去重和出站队列。开局与终局消息分别有业务去重键，避免消息重试产生多个房间或重复结算。
- 不把完整数据库对象 `asdict` 后发给客户端。显式构建公开视图，再仅为本人附加本人手牌；同一房间不同接收者得到不同快照。
- SSE 逐连接绑定请求提供的员工 UID，每次重连先权威快照再订阅。不能共享包含某位玩家手牌的缓存响应或广播包；HTTP 响应禁止公共缓存。
- 所有操作携带房间 ID、局次 ID、状态版本与唯一请求 ID。以数据库行锁和幂等记录处理抢座、准备、叫分、出牌、托管、再来一局和终局。
- 定时器与手动动作走同一状态转移入口，以服务端时间决定截止。服务重启按持久化截止恢复，不能重置每步倒计时。
- 前端只提供选中的牌 ID；后端检查它们确实属于该玩家、不重复、轮次正确且牌型合法，不能相信客户端的牌型或剩余张数。

## 7. 状态、异常与恢复

状态：等待入座／准备 → 叫分 → 出牌 → 结算；未开局房间可取消，结算后经三人重新准备进入新局次。

- 群消息发送失败：仍由已有出站机制有限重试；未送达不能抢座，10 分钟到期关闭，不能无上限重试阻塞消息队列。
- 争抢最后席位、重复点击准备、同时出牌／超时：一次事务胜出，其他请求返回已处理或过期状态。
- 版本冲突／迟到请求：不扣牌、不推进回合，刷新快照并保留明确错误提示。
- 单次请求失败：客户端不能自行认定已出牌，按请求 ID 查询或重试，不能重复出牌。
- 全不叫与无人操作：按叫分重发上限和托管推进；不调用付费 AI。
- 等待房退出：释放非房主席位、清空准备；已有玩家不因别人离开失去身份。开局后不释放席位。
- SDK UID 暂不可用：暂停客户端请求并允许重试读取；服务端对局和时钟继续，不因客户端重连重置。
- 结果由服务器一次性生成，双方农民共享同一胜负判定；显示玩家名称和中文原因，不对外展示错误编码或长 UUID。

## 8. 验收与发布

1. 规则单测：每种牌型、相同牌数比较、顺子边界、飞机翅膀限制、四带二与炸弹区分、连续两次不出、春天／反春。
2. 随机性质测试：54 张牌不重不漏、手牌与已出牌守恒、每个自动提示合法、每局次不能重复结算。
3. UID 接入测试：缺失／格式无效／不存在／未入职的 UID 明确拒绝；正常观众 UID 不获得手牌，不得操作玩家席位。记录已知限制：伪造有效玩家 UID 无法被识别，不把它列为已防御能力。
4. 并发与计时测试：三人抢两位、最后席位、第三次准备、超时与点击竞态、重发与重启恢复、旧局请求进入新局。
5. 视图隔离测试：三个独立玩家加一名观众，分别使用自身 UID 检查 HTTP 和 SSE 响应，只包含该 UID 所在席位的手牌；开发日志不能包含隐藏手牌。不将此测试解释为防 UID 冒充。
6. UI 自动化：真实沙箱限制下选牌、滑选、出牌、提示、不出、聊天、返回列表、重连；手机 390px／窄屏 320px 和桌面均无遮挡、无横向溢出。
7. 真机验收：使用独立 Gamefy 卡，三名不同账号完整玩一局，测试 SDK UID 读取、重开恢复及观战。预览环境不能替代正式玩家验证。
8. 发布前备份数据库和代码；新增表为增量迁移。先测试群验收，再按用户批准开放小游戏群。部署确认不影响象棋、已有 bot 指令和群消息时延。

首版成功标准：三人可完成一局并继续新局；掉线可恢复而不重置牌或计时；正常客户端以自身 UID 请求时只收到自身席位手牌，观众不收到手牌（不保证防 UID 冒充）；终局群通告一次；不产生摸鱼币流水、不调用付费 AI。
