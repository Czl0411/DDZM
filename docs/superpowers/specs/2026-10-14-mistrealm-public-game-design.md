# 雾境公开双人卡牌游戏接入设计

日期：2026-10-14
状态：用户已确认；本地实现和验收完成，平台绑定及发布待新游戏卡 ID。

## 1 已确认的目标

将《雾境：王冠与群鸦》作为 DDZM 项目的第四个独立 Gamefy 游戏接入，与象棋、斗地主、你画我猜并列。用户将在平台新建游戏卡，提供其 ID 或链接后绑定发布配置。

面向所有能够通过 Gamefy SDK 取得 UID 的平台玩家开放。明确采用 UID 信任模式，不获取或验证玩家 token；不要求入职，不读取员工表，不关联公司积分、工资、权限或群聊。昵称与头像只用于展示。UID 为客户端声明，不能证明身份，此边界已由用户确认。

玩家在游戏内创建或加入房间，不依赖机器人群指令。复用现有 FastAPI、SQLAlchemy、数据库迁移和部署服务，不新建独立微服务，不修改现有游戏规则。

## 2 实现范围与方案选择

采用独立游戏模块接入现有后端：比另建服务器更容易沿用部署与测试体系；比直接复制斗地主模块更适合去除员工、群消息及奖励耦合。仅复用已存在的模式，不抽象通用游戏框架。

首版交付：加载与首页、创建或输入房间码加入、房间准备、阵营选择、换牌、预备牌选择、三局对战、局末结果、整场结算、再战、规则与图鉴、刷新恢复。双方均可选择任一阵营，允许同阵营镜像对局。

不包含：匿名游客、公开房间列表、观战、聊天、匹配排位、自由构筑、AI 对手、积分奖励、群指令和自动上架。公开指所有平台玩家可参与，不代表必须公开全部房间。

## 4 玩家与房间流程

1. 主脚本开始即上报真实加载状态。取得 SDK 玩家资料，登记独立玩家；失败提供重试，不随机创建匿名身份。
2. 首页显示开始对战、图鉴、规则及设置。开始对战展开创建房间和加入房间，不增设无作用的跳转页。
3. 创建房间后，创建者为房主且占据席位 0；返回房间 UUID 与 6 位数字加入码。邀请码不得当作玩家身份。
4. 另一名玩家输入加入码，占据席位 1。同一 UID 重复进入恢复原席位，不能同时占两个席位。
5. 双方选择阵营和固定预组并准备；修改阵营取消本人的准备。房主只能在两人均准备后开始。
6. 开始后房间禁止新玩家加入。离线者仍占席，刷新可恢复。
7. 结算后双方点击再战才回到准备阶段；保留房间与阵营，清空准备标记，重新开始时生成新比赛 ID、洗牌与随机先手。
8. 等待阶段房客退出释放席位，房主退出关闭房间；比赛中退出必须确认，按认输处理。结算阶段允许返回首页。

每 UID 最多拥有一个未关闭房间席位；创建或加入前返回其现有房间，引导继续或明确退出，避免产生孤立房间。

等待房间 30 分钟无人操作即关闭；结算房间保留 30 分钟用于再战。加入码在活动房间间唯一；关闭后失效。仅参与者可以读取房间状态，未入座者通过加入码申请加入，不通过猜 UUID 读取对局。

## 5 玩法与卡池

延续已给出的 V0.1 玩法文档。以下为实施所需的权威规则摘要。

每套预组 20 张，16 单位、4 战术；同名牌各两张。中立 6 种共 12 张，阵营专属 4 种共 8 张，领袖不入牌库。无费用、攻击或连锁系统。

每人前后两列，每列最多 6 个单位。总战力为当前战力之和，护甲不计分。行内位置没有规则意义。卡牌实例 ID 唯一，不能只用卡名标识两张同名牌。

### 5.2 开局与局间

- 先随机先手，公开结果；各抽 9 张，各可一次换掉 0 至 2 张。换牌先补抽，再将换掉牌洗回，以免抽回同一实例。
- 两人均完成换牌后，从各自手牌选 1 张预备牌，余下 8 张开始第一局；对手看不到选牌过程或内容。
- 第一局先手首次打出单位，部署完成后该单位获得 2 增益；标记只限第一局。
- 第二局各抽 3 张，无换牌；第三局各抽 3 张并取回预备牌。剩余手牌跨局保留。
- 上一局胜者先手；平局交换上一局先后手。
- 局末所有单位移入弃牌堆，清除临时战力和护甲；领袖使用状态跨局保留。

### 5.3 行动与目标

一次行动为打出一张牌、使用领袖或停手。停手本局不可撤回；另一方可连续行动直至也停手。无手牌但领袖仍有合法目标时可使用领袖，否则只能停手。

单位先进入合法战列再结算部署；无合法目标时部署跳过而单位保留。有合法目标时不能省略必选目标。战术无合法目标时不可打出。不同目标不得重复；至多两目标效果选择 1 至 2 个合法目标，单位部署没有目标时选 0 个，战术至少有 1 个；灰烬统领满足条件时必须选择两个其他同列友军。这明确区分“至多”效果与强制双目标效果。

满列不能放入单位，不能以丢弃手牌代替行动。客户端提交牌实例、战列与目标，后端校验归属、时机、数量、范围及条件。非法行动不消耗牌、不改变版本、不重置倒计时。

### 5.4 计分

内部采用整数半分：胜者加 2、败者加 0、平局双方各加 1；显示除以 2，得到原规则中的 1 分与 0.5 分。最多三局；分差大于剩余局数乘 2 时提前结束。三局后同分为整场平局。战力差不影响局分。

认输或超时认输直接结束整场并标记结束原因，不伪造尚未发生的单局比分。

## 6 状态机与超时

阶段为 waiting → mulligan → reserve → playing → round_result → playing 或 finished。第三局开始时自动取回预备牌。closed 是房间终止状态。

以下是实施默认值，区别于此前已确认的核心规则：

- 换牌阶段 45 秒，未提交者视为换 0 张。
- 预备阶段 30 秒，未提交者由服务端从其手牌均匀随机选择 1 张；确定一次后保存，不在刷新时重选。
- 每次行动 45 秒，超时按本局停手处理。
- 同一玩家连续两次需要其输入的准备或行动阶段超时，按整场认输处理；一次有效主动提交清零其超时计数。同时达到认输条件则整场取消，不算任一方获胜。
- round_result 展示 5 秒后进入下一局；最终结果停留至玩家操作。
- 断线不重置倒计时；刷新只恢复服务端状态。

以服务端绝对时间为准。沿用后台推进方式，并在读写状态时推进已到期阶段；阶段转换使用上一次截止时间建立下个截止时间，不能因请求或服务恢复重新获得完整时长。随机选择作为输入传入纯状态转换函数，便于可重复测试。

## 7 数据持久化

新增独立实体，全部使用 mistrealm 前缀，不对 UserRecord 或群消息表建立外键。

- Player：UUID 主键、唯一 platform_uid、显示昵称、可选头像 URL、创建及最近活动时间。
- Room：UUID 主键、唯一活动加入码、房主玩家 ID、阶段、版本、当前比赛 ID、完整私有状态 JSON、创建及到期时间。
- Seat：room_id、seat_index、player_id，约束同房席位唯一、同玩家活动席位唯一；房间关闭时释放。席位信息以此为成员关系权威来源，不另维护一套互相矛盾的玩家数组。
- Request：玩家 ID、request_id、请求摘要、关联房间、处理结果，用于创建、加入及对局动作的幂等处理。

比赛结果与每局比分存于房间状态；首版不建排行榜或通用统计表。请求去重键不能只按房间和 request_id，必须包含玩家，防止不同玩家请求碰撞。

所有变更在事务中锁定房间；创建或加入同时锁定玩家，处理同 UID 同时加入两个房间的竞争。版本匹配后才更新，重复请求先查回执，不重复扣牌、换牌或结算。相同 request_id 携带不同参数返回冲突。

## 8 接口与同步

路径统一为 `/api/mistrealm`，请求头为 `Authorization: MistrealmUid <uid>`。校验非空、长度与字符格式，不把格式校验描述为 token 验证。用户资料由独立登记接口创建或更新。

| 方法与路径 | 功能 |
| --- | --- |
| POST /players/me | 登记或更新昵称头像，不访问员工表 |
| GET /players/me | 当前公开资料及可恢复房间 |
| POST /rooms | 创建房间，支持 request_id |
| POST /rooms/join | 用 6 位加入码加入，支持 request_id |
| GET /rooms/{id} | 当前玩家可见的房间快照 |
| POST /rooms/{id}/actions | select_faction、ready、unready、start、mulligan、reserve、play、leader、pass、concede、leave、rematch |
| GET /rooms/{id}/events | SSE 返回当前接收者的快照，版本变化才发送 |

动作封装包含 match_id（等待阶段可为空）、version、request_id、action、payload；每个 action 严格限定 payload 字段。比赛 ID 阻止上一场的延迟请求作用于再战。

错误分层：身份缺失 401，非参与者 403，不存在或加入码失效 404，状态或版本冲突 409，参数错误 422，限流 429。冲突后重新获取快照，不能自动重放一次新的出牌。

SSE 采用 fetch 流以支持 Authorization 头；断流后有限退避重连，先读取完整快照。持续失败时退化为低频快照轮询，恢复后停止轮询，避免两套通道同时运行。心跳不增加房间版本。

创建和加入入口设置保守的初始限流：每 UID 每分钟创建最多 5 次、加入尝试最多 20 次；动作每 UID 每分钟最多 120 次。多进程部署时限流统计须共享，不把单进程字典当全局限制；UID 限流仅用于减少误操作，不能宣称防止伪造身份。

## 9 隐藏信息与沙箱

对玩家 A 仅返回 A 的手牌及其预备牌内容；B 的手牌和预备区仅返回数量或存在状态。双方牌库均不返回顺序或尚未抽到的实例。事件记录只包含公开操作，不记录对手换掉或预备的牌。结束后也不自动揭示隐藏牌。

昵称通过 textContent 渲染，限制长度；头像只接受合法 HTTPS URL，失败使用默认图，不由服务器抓取头像。

遵守 Gamefy 的 iframe 沙箱约束，不使用 localStorage、sessionStorage、IndexedDB、Cookie 或 URL hash。KV 只存当前 UID 对应的最近房间 ID 与本地显示偏好，不把客户端存档当权威牌局。KV 失败仍可通过服务端的当前房间恢复。

首屏仅加载必要资源。SDK 和首屏失败有可重试提示；显示可交互首页后才 loading.ready。进入房间前 await 登记和服务端响应，不在失败时显示已成功入座。

## 10 真实界面与资源

三张已生成的效果图是美术方向，不直接作为带点击热区的整屏页面。DOM/CSS 构建菜单、卡位、卡牌、状态与按钮。动态战力、护甲和技能文字由结构化数据渲染，不能依赖图片里的固定数字。

卡图用于图鉴与角色插画；战场采用精简卡面、动态数值，点选或长按查看完整技能。需要的纯背景和插画资源在实现阶段单独导出或生成，避免把旧文字重复叠在动态 UI 下。资源使用 ASCII 文件名和相对路径。

桌面布局沿用四战列与侧栏；手机竖屏改为紧凑战列、可横向浏览的手牌和点选详情，关键停手与确认按钮保持可触达，不强制用户旋转。至少检查 390×844、844×390、1366×768。

本地现有美术：16 张卡牌 PNG、首页／房间／对战三张效果图。原始大图留存，发布资产控制体积并按需加载；具体发布限制以当前 CLI dry-run 和平台文档为准。

## 11 文件边界

新增前端：`gamefy/mistrealm/publish/{index.html,style.css,game.js,client.js,config.js,cards.json,assets/}`，配套 `tests/`、README、独立 Gamefy 配置。

新增后端：`mistrealm_cards.py`（卡池）、`mistrealm_state.py`（纯规则）、`mistrealm_repository.py`（事务与视图）、`mistrealm_api.py`（HTTP 与 SSE）。卡池以一个受版本控制的数据源为准，生成前后端所需静态数据并用测试校验一致，避免手工维护两份技能数值。

最小修改已有文件：schema、repository 的 mixin 入口、app 路由与超时推进、runtime settings、数据库迁移及相关部署配置。新增 `DZMM_MISTREALM_ENABLED` 控制 API 启用，默认关闭；不以未获得的游戏卡 ID 阻塞本地规则及接口测试。

不改 commands、员工查找、工资、奖励与既有游戏 UI。服务器公网代理仅新增 `/api/mistrealm/` 路径，不扩大管理接口暴露范围；SSE 禁止缓冲与缓存。

用户尚未提供新游戏卡 ID，因此绑定配置和平台发布是最后的外部接入步骤。开发时不能填写其他游戏的 ID 或假造 ID。用户确认发布前不部署线上、不运行生产迁移、不提交公开上架。

## 12 验收标准

### 规则与状态

每张卡的效果和条件边界有测试；覆盖护甲、过量伤害、摧毁、满列、重复目标、错误战列、敌我目标限制、领袖一次性、先手补偿只触发一次、两种阵营及镜像对局。

覆盖换牌不抽回同一实例、两人准备屏障、预备牌第三局取回、手牌跨局保留、局末清理、2∶0、三局决胜、单局与整场平局、停手后连续行动、认输、超时和再战。

### 接口与持久化

未入职且员工表中不存在的 UID 可完成登记、建房和整场比赛。测试证明员工表不增加记录，公司积分不变化。

使用两个独立 UID 验证隐藏信息隔离；未入座 UID 不得读取房间。重复请求、过期版本、过期比赛 ID、同时抢最后席位、同 UID 跨房加入、重连快照和事务回滚均有测试。

用实际 PostgreSQL 验证行锁和唯一约束竞争，不能仅用 SQLite 单线程测试宣称并发正确。迁移升级、回退在测试库验证；不动生产数据。

### 前端与集成

真实操作走通：首页 → 建房／加入 → 选阵营 → 双方准备 → 换牌 → 预备牌 → 三局对战 → 结算 → 再战。使用两客户端检查同步，中途刷新双方都恢复正确状态。

覆盖接口失败、SDK 失败、KV 失败、SSE 断线、图片失败；按钮可重试，不能重复提交。确认移动端无关键按钮遮挡、卡牌详情可读。

新增用例通过后运行受影响的 core、runtime、deploy 测试与现有三个游戏的相关回归测试。平台 gamefy check/dev 双玩家检查、弱网和刷新检查应在绑定新游戏卡后完成；真实普通账号验证与本地测试分别报告。

## 13 评审结论与下一步

本设计落实已经确认的公开访问、独立玩家、UID 信任及游戏内建房要求。需要评审的新增默认行为主要是超时策略、首版不做观战与公开房间列表，以及手机布局。

书面设计确认后，编写逐步实施计划并按规则引擎、持久化接口、前端交互、双客户端验收的顺序推进。游戏卡 ID 到位后绑定新卡并做平台联调；不使用旧游戏卡代替。
